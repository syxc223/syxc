**一句话架构**：云服务器只做"账号 + 房间介绍所"，拿到 Host IP 后两名玩家走 **Netcode P2P 直连**（UDP 7777），所有游戏状态由 Host 侧服务器权威写。

### 0.4 三类网络通信原语（整个项目的网络设计骨架）

| 原语 | 方向 | 本项目的典型用法 | 代码 |
|---|---|---|---|
| `NetworkVariable<T>` | 服务器写 → 全员读 | 同步"状态"：门开合、压力板按压、出口状态、朝向、位置 | `_isOpen`、`_isPressed`、`_p1InExit`、`SyncFacing` |
| `ServerRpc` | 客户端 → 服务器 | 客户端"请求"：我要拾取箱子、我要确认任务、我移动到了这里 | `TryPickupServerRpc`、`ConfirmMissionServerRpc`、`UpdateTransformServerRpc` |
| `ClientRpc` | 服务器 → 客户端 | 服务器"通知"：谜底文字、掉血数值、传送落地、点对点传送 | `ShowInvestigationClientRpc`、`ApplyTeleportClientRpc` |

三条铁律（本项目严格遵守，也是论文"网络架构"一节的核心论点）：
1. **只有 `IsServer` 分支写 `NetworkVariable`**；
2. 跨端请求一律 `[ServerRpc(RequireOwnership = false)]` + `ServerRpcParams.Receive.SenderClientId` 识别真实发送者（**绝不用 `LocalClientId`**）；
3. `OnValueChanged` 订阅放 `OnNetworkSpawn`、**必须**在 `OnNetworkDespawn` 退订（否则重连后回调叠加）。

## 1. 用户模块

### 1.1 涉及文件

| 层 | 文件 | 职责 |
|---|---|---|
| UI | `Scripts/UI/LoginPanel.cs` | 登录 / 注册表单、本机 IP 显示 |
| HTTP | `Scripts/Network/ApiClient.cs` | REST 基类、JWT 持久化、401 兜底、`StaticCoroutine` |
| 业务 | `Scripts/Network/AuthApi.cs` | 注册 / 登录语义封装 |
| 服务端 | `server/routes/auth.js`、`server/middleware/auth.js`、`server/db.js`（users 表） | 账号与令牌 |

### 1.2 `LoginPanel`：视图与本地校验

- `Start()` 里用代码挂按钮回调（`_loginButton.onClick.AddListener(...)`），并把注册面板 `SetActive(false)`；同时显示本机 IP：`_ipText.text = $"Your IP: {GetLocalIP()}"`。
- 注册前做三层**本地**校验（长度、两次密码一致），不通过就直接 `ShowRegMessage` 返回 —— **省一次网络往返**，与后端校验（`routes/auth.js`）形成"前端体验优化 + 后端强制约束"的双层校验。这是论文可讲的"输入校验设计"。
- 请求期间 `SetButtonsInteractable(false)` 防重复提交（幂等保护）。
- 成功后不自己切换界面，而是 `OnLoginSuccess?.Invoke(uname)` 交给 `UIManager`（**事件回调解耦**）。
- `GetLocalIP()`：**UDP 连接法**——`Socket.Connect("8.8.8.8", 65530)` 不真正发包，只让系统选出出网网卡，再读 `LocalEndPoint`；失败则退化为 DNS 枚举（`Dns.GetHostEntry`）。`RoomPanel` 里是**三重**探测（多一层网卡枚举并跳过 Virtual/VMware/Hyper-V/Docker 虚拟网卡）。

### 1.3 `ApiClient`：静态 HTTP 基类（本模块的技术核心）

```csharp
public const string ServerUrl = "http://8.130.65.176:3000";   // 云端
public static string Token => PlayerPrefs.GetString("jwt_token", "");
public static bool IsLoggedIn => !string.IsNullOrEmpty(Token);
```

设计要点：

1. **签名即状态**：`Token` 直接读 `PlayerPrefs`，`IsLoggedIn` 就是一个表达式。`UIManager.Start` 用它实现"**自动登录**"（关掉游戏再打开仍在已登录态）。
2. **三个动词一个出口**：`Get`/`Post`/`Delete` 都构造 `UnityWebRequest` → 统一交给 `SendRequest` 协程 → 统一回调签名 `Action<bool, string>`（成功标志 + 响应体）。**错误处理只写一遍**。
3. **统一鉴权**：`AttachAuth` 给每个请求加 `Authorization: Bearer <token>`。
4. **401 全局兜底**（很值得讲的一处）：
   ```csharp
   if (req.responseCode == 401) { ClearAuth(); UIManager.Instance?.ShowLogin(); }
   ```
   令牌过期/失效时，任何一条业务接口都会自动把玩家踢回登录界面，**业务代码零感知**。这就是"横切关注点集中在基类"的收益。
5. **错误信息抽取**：成功取 `downloadHandler.text`；失败优先取响应体（后端是 JSON `{success:false,error:"..."}`），取不到才用 `req.error`。
6. `StaticCoroutine`：静态类无法 `StartCoroutine`，于是**按需自建一个隐藏的常驻 GameObject** 作为协程宿主（懒加载 + `DontDestroyOnLoad`）。这是"静态工具类需要协程"的标准解法，可以当作一个小亮点讲。

### 1.4 `AuthApi`：业务语义封装

- `Register` / `Login` 各一个方法，内部 `JsonUtility.ToJson(new NetworkModels.AuthRequest{...})` → `ApiClient.Post`。
- 回调再收敛一层：成功就 `SetToken/SetUsername` 落盘，回调给 UI 的是 `(bool success, string username, string error)` —— **UI 只关心"成不成、谁、为什么失败"**，完全不碰 HTTP 细节。
- `TryExtractError` 用 `JsonUtility.FromJson<AuthResponse>` 解析 `error` 字段，解析失败就原样返回 body（容错）。
- ⚠️ 注意：**注册成功也是直接给 token**（服务端也返回 token），所以注册后即登录态。

### 1.5 服务端：`routes/auth.js` + `middleware/auth.js`

```
POST /api/auth/register
  ① 空值 → 400 ｜ 用户名 3-20 → 400 ｜ 密码 6-32 → 400      （与客户端校验一致，但这里才是强制）
  ② SELECT id FROM users WHERE username=?  → 命中 → 409 "用户名已存在"
  ③ bcrypt.hashSync(password, 10)  → INSERT users
  ④ jwt.sign({userId, username}, JWT_SECRET, {expiresIn:'24h'}) → 返回 {success,token,username}

POST /api/auth/login
  ① 查用户 → 无 → 401 "用户名或密码错误"    ┐ 两者返回同一个错误文案，
  ② bcrypt.compareSync → 失败 → 401 同上    ┘ 不泄露"账号是否存在"
  ③ 签发 24h JWT
```

`middleware/auth.js`：从 `Authorization: Bearer xxx` 取令牌 → `jwt.verify(token, process.env.JWT_SECRET)` → 成功把 `decoded` 挂到 `req.user` 供后续路由使用（`req.user.userId`）；失败统一 401。

`server.js` 的**启动自检**（安全设计，答辩可讲）：

```js
if (!process.env.JWT_SECRET || process.env.JWT_SECRET.startsWith('change_this') || process.env.JWT_SECRET.length < 32) {
  console.error('[FATAL] JWT_SECRET 缺失或过弱...'); process.exit(1);   // 拒绝启动
}
```

再叠加 `express-rate-limit`：**登录/注册 10 次/分钟/IP，房间接口 60 次/分钟/IP** —— 这是防暴力破解的直接手段。

### 1.6 本模块可讲的三个设计点

1. **前后端双层校验**：UI 先校验（体验），服务端再校验（安全），服务端才是唯一可信边界。
2. **令牌生命周期集中管理**：`ApiClient` 一处负责存/取/清 + 401 兜底，业务层无感。
3. **横切关注点集中**：鉴权头、超时（10s）、错误抽取、协程宿主都在基类。

## 2. 房间管理模块

### 2.1 客户端：`RoomPanel`

| 交互 | 方法 | 链路 |
|---|---|---|
| 进入面板 | `OnEnable` | 显示欢迎语 + 本机 IP → `SetInteractable(true)` → `RefreshRooms()` |
| 刷新列表 | `RefreshRooms` | 清空子物体 → `RoomApi.GetRooms` → 逐条 `Instantiate(_roomItemPrefab)` 填充 `RoomNameText / HostNameText / PlayerCountText` + Join 按钮 |
| 建房 | `OnConfirmCreate` | `GetLocalIP()` → `RoomApi.CreateRoom(name, ip)` → `CurrentRoomId = roomId` → `GameManager.StartHost()` |
| 加房 | `OnJoinRoom` | `RoomApi.JoinRoom(roomId)` → 拿 `hostIp` → `GameManager.Connect(ip)` |
| 直连 | `OnDirectConnect` | 跳过 API，`CurrentRoomId = -1` → `Connect(手输 IP)` |
| 登出 | `OnLogoutClick` | `ApiClient.ClearAuth()` → `UIManager.ShowLogin` |

两个细节值得讲：
- **满房降级显示**：`if (!room.CanJoin)` 时把 Join 按钮 `interactable = false` 并改文案为"已满"（`RoomInfo.CanJoin` 是 DTO 上的表达式属性：`current_players < max_players && status == "waiting"`）。
- **空列表占位行**：服务器不可达时 `ShowEmptyRooms("暂无可用房间 (服务器未连接)")` 用同一 prefab 造一条禁用行，**避免"列表空着玩家不知道是没房间还是没网"**。这是很好的交互细节。

### 2.2 `RoomApi` + `NetworkModels`

- `NetworkModels` 是纯 DTO 集合（`[Serializable]`），字段名**故意与后端 JSON 一致**（`host_ip`、`current_players`…），因为 `JsonUtility` 按字段名映射，不做命名转换。
- `RoomApi` 与 `AuthApi` 同构：五个方法对应五个端点，回调统一 `(bool success, 数据..., string error)`。`TryExtractError` 用 `SimpleResponse` 兜底解析。

| 客户端方法 | HTTP |
|---|---|
| `GetRooms` | `GET /api/rooms` |
| `CreateRoom` | `POST /api/rooms` body `{name, hostIp}` |
| `JoinRoom` | `POST /api/rooms/:id/join` |
| `LeaveRoom` | `POST /api/rooms/:id/leave` |
| `CloseRoom` | `DELETE /api/rooms/:id` |

### 2.3 服务端：`routes/rooms.js`

整个路由文件顶部 `router.use(authMiddleware)` —— **房间接口全部需要登录**。

**建房 `POST /`**
```js
校验 name / hostIp 非空 + net.isIP(hostIp) 合法 + name ≤ 32 字
DELETE FROM rooms WHERE host_user_id=? AND status='waiting'   // 只清自己的"等待中"房间，不动进行中的
INSERT rooms (..., max_players=2, current_players=1, status='waiting')
INSERT room_members (room_id, host_user_id)                   // 房主计入成员
INSERT players (..., 对局记录，失败静默)                        // 仅作持久化留痕
```

**加房 `POST /:id/join`**：房间存在且未关闭 → 未满 → `INSERT OR IGNORE room_members` → `current_players+1, status='playing'` → `touchRoom` → 返回 `{hostIp, host_username}`。**返回的是 Host 的公网/局域网 IP，客户端拿它去 Netcode 直连**。

**离开 `POST /:id/leave`**：先查 `room_members` 确认"你确实在这个房间"（**防越权**）→ 房主离开则整房删除（外键 `ON DELETE CASCADE` 级联清成员）；普通成员离开则人数 -1、状态回 `waiting`、若归零删除。

**关闭 `DELETE /:id`**：仅房主可关（否则 403）。

**表结构（`db.js`）**

```
users(id, username UNIQUE, password_hash, created_at)
rooms(id, name, host_user_id, host_ip, host_username, max_players=2, current_players, status, last_activity, created_at)
room_members(room_id, user_id, joined_at)  PK(room_id,user_id)   -- 复合主键天然去重
players / missions / mechanisms / items / chat_messages            -- 对局与关卡配置留痕
PRAGMA journal_mode = WAL; PRAGMA foreign_keys = ON;
```

两个工程细节：
- **`data/` 目录启动前自建**（`fs.mkdirSync(dataDir, { recursive: true })`），否则全新部署直接崩。
- **过期房间清扫**（`server.js`）：`setInterval(sweepStaleRooms, 5min)`，删除 `last_activity` 早于 10 分钟的房间。`touchRoom()` 在 join/leave 时刷新该字段。=> **僵尸房间不会永久占列表**。
- **`missions` / `mechanisms` / `items` 用 `INSERT OR IGNORE` 播种**（幂等，可重复启动），与 `seed.sql` 保持一致。

### 2.4 关键设计取舍：房间只是"介绍所"

后端**不转发任何游戏数据**，也不做中继/反代。它解决的是"玩家怎么找到对方"，解决后就退出链路：

```
Unity ──HTTP/auth──▶ 云服务器（JWT 鉴权）
Unity ──HTTP/rooms─▶ 云服务器（房间列表 / host_ip）
Unity ──UDP 7777───▶ 直接连到 Host（游戏数据全部 P2P）
```

好处：服务器零游戏负载、延迟最低、毕设成本最低；代价：需要 Host 可被直连（局域网/公网端口放行），这也是项目里保留 `EchoTester`（TCP 3001 连通性自检）与"手输 IP 直连"入口的原因。

## 3. 网络模块（本项目最核心的模块）

### 3.1 `GameManager`：连接、场景、断线的总调度

**生命周期**：`Awake` 单例 + `DontDestroyOnLoad`；`Start` 取 `UnityTransport` 并订阅 `OnClientConnectedCallback` / `OnClientDisconnectCallback`。

**与后端+房间的三方关系**：`CurrentRoomId`（默认 -1 = 直连模式）只用于 `ExitRoom` 时通知服务器"我走了"。

**Host 启动 `StartHost()`**
```csharp
_selfTransport.SetConnectionData("0.0.0.0", 7777, "0.0.0.0");  // 绑全部网卡
NetworkManager.Singleton.StartHost();
RegisterSceneEvents();
StartCoroutine(LoadGameScene());   // → SceneManager.LoadScene("大厅", Single)
```

**Client 连接 `Connect(ip)`**
```csharp
_selfTransport.SetConnectionData(ip.Trim(), 7777);
NetworkManager.Singleton.StartClient();
RegisterSceneEvents();
_connectTimeout = StartCoroutine(ConnectTimeout());   // 15 秒连不上就放弃
```

**连接超时（15s）**：`ConnectTimeout` 等待 15 秒后若 `!IsConnectedClient` → `Shutdown()` + `ReturnToLobbyAfterDisconnect()`。注释里说明了为什么超时后**还要手动回大厅**：客户端从未真正连上时，`Shutdown` 不一定触发 `OnClientDisconnectCallback`。→ 这是"**不依赖回调一定会来**"的防御式写法。

**`ReturnToLobbyAfterDisconnect`**：`yield return null` **等一帧**再 `ExitRoom()`，避免在 Netcode 回调栈里调用 `Shutdown`（重入风险）。这类"回调里不干重活"的经验值得讲。

**重入保护 `RegisterSceneEvents`**：`_sceneEventsRegistered` 布尔量保证 `OnLoadComplete` 只订阅一次；`ExitRoom` 里退订并复位。→ 对应论文"事件订阅生命周期管理"。

**场景加载：全部由服务器发起**，客户端跟随：
```csharp
NetworkManager.Singleton.SceneManager.LoadScene("大厅", LoadSceneMode.Single);
```
> 关键坑（已解决）：**玩家 NetworkObject 跨场景保留**（不随场景卸载销毁，`OnNetworkSpawn` 只跑一次）→ 所以每进一个场景，**必须由服务器显式把玩家传送到出生点**：`GameManager.OnSceneLoadComplete`（大厅：`TeleportPlayer(0/1, ...)`）与 `LevelManager.OnNetworkSpawn`（各关卡：`_p1Spawn/_p2Spawn`）。这就是"为什么传送要通过 `PlayerMove.ServerTeleport`"的根因。

### 3.2 `PlayerMove`：一个 NetworkBehaviour 承担玩家的一切

这是全项目最复杂的脚本，建议按"**职责清单**"讲：

| 职责 | 关键实现 |
|---|---|
| 移动 | `CharacterController.Move`，速度 `speed=5`，输入 `Input.GetAxis("Horizontal"/"Vertical")` |
| 重力 | 手写 `_verticalVelocity`（`gravity=-25`、`maxVelocityY=-40`、落地贴地 `groundSnapForce=-2`） |
| 朝向动画 | 四方向判定 → `facing` 整数（0 idle / 1 down / 2 up / 3 left / 4 right），播放走 `_animator.SetInteger("facing", …)` |
| 相机跟随 | 阻尼跟随 + 球检测防穿墙 + 锁 Yaw |
| 脚步声 | 每 `footstepInterval=0.35s` 且在地面时 `PlaySfxAt(pos,"Footstep", pitchVar)` |
| 位置同步 | 节流上行 + 非 owner 硬覆盖 |
| 传送 | `ServerTeleport` + 定向 ClientRpc |
| 推箱 | `OnControllerColliderHit` + `PushCubeServerRpc` 中继 |
| 双人外观 | `ApplyPlayerAppearance(pNum)`（P2 换 AnimatorController + 精灵） |

**（1）状态同步：为什么不是"每帧同步位置"**

```csharp
void UpdateTransform() {                    // owner 侧
    _syncTimer += Time.deltaTime;
    bool movedEnough = (transform.position - _lastSentPos).sqrMagnitude > 0.01f;   // ≈0.1m
    if (_syncTimer < _syncInterval /*0.1s*/ && !movedEnough) return;               // 双条件节流
    ...
    if (IsServer) { SyncPos.Value = transform.position; SyncRot.Value = transform.rotation; }
    else          { UpdateTransformServerRpc(transform.position, transform.rotation); }
}
```
**定时（≤10 次/秒）+ 位移阈值（>0.1m 立刻发）** 双条件：静止时不发、微动时不发、走起来保证 ≤10Hz。相比"每帧 60 次 RPC"，带宽下降一个数量级（论文"网络优化"一节的实测点）。

非 owner 侧：
```csharp
void FixedUpdate() { if (IsOwner || !_spawned) return; SyncTransform(); }
void SyncTransform() { transform.position = SyncPos.Value; transform.rotation = SyncRot.Value;
                       _animator.SetInteger("facing", SyncFacing.Value); }
```
即"**owner 自己算，别人不动**（服务器权威）"：owner 的位置由本人本地驱动，其他人靠 NetworkVariable 覆盖。

⚠️ **由此推出一个必然结论**（答辩常被问）：任何"本地直接改非 owner 的 transform"都会被下一物理帧拉回，所以**传送必须走服务器**：

```csharp
public void ServerTeleport(Vector3 pos) {          // 服务器调用
    if (!IsServer) return;
    _cc.enabled = false; transform.position = pos; _cc.enabled = true;   // CC 必须开关一次
    SyncPos.Value = pos; SyncRot.Value = transform.rotation;             // 通知非 owner
    ApplyTeleportClientRpc(pos, new ClientRpcParams{ Send = new ClientRpcSendParams{
        TargetClientIds = new[]{ OwnerClientId } } });                   // 通知 owner 本人
}
```
**为什么需要定向 ClientRpc？** 因为 owner 本地**从不读 `SyncPos`**（它自己就是数据源），只写 NetworkVariable 对 owner 无效 —— 必须再发一条只给 owner 的 ClientRpc 让本人落地。这个"NetworkVariable 对 owner 无效 + 定向 ClientRpc 补位"的细节非常适合讲。

**（2）动画同步**：`SyncFacing` 是 `NetworkVariable<int>`，owner 变化时上报（服务器直接写 / 客户端 `SetFacingServerRpc`），非 owner 通过 `OnFacingChanged` 订阅驱动 Animator，同时 `SyncTransform` 里也兜一次。→ "状态驱动动画，而不是同步 Animator 参数流"。

**（3）相机跟随（HD2D 手感的关键）**

```
desired = player + offset(0, 4.5, -6)                 // 固定 50° 俯角风格
① CameraBounds.Active.ClampZ(desired.z)               // 每场景 Z 夹取（防镜头穿到墙外）
② 从玩家上方 2.3m 向 desired 做 SphereCast（半径 .25，忽略 CameraIgnore 层）
      命中→ 把镜头收到墙前（至少 0.8m）
③ desired.z = Min(desired.z, player.z - 0.45)         // 锁"镜头永远在玩家北侧"
   desired.y = Max(desired.y, player.y + 2.8)         // 锁"镜头不低于玩家 2.8m"
   lookDir.z ≥ 0.35                                    // 视线 Z 分量下限 → yaw 永不掉头
④ 距离 > cameraSnapDistance(6m) → 直接就位（出生/传送不甩尾）
   否则 → 指数阻尼 k = 1 - exp(-speed*dt)（帧率无关插值）
```
第 ③ 步是**踩坑修出来的**：早期"镜头越过北墙会被物理推到玩家南侧 → 镜头掉头 180° → W/A/S/D 方向反转"。用"钳制视线前向半球"从根上消除，而不是靠调参。**这是答辩里很好的"问题—分析—解决"案例**。

**（4）推箱（`PlayerMove` 与 `PickupCube` 的协作）**
```csharp
void OnControllerColliderHit(ControllerColliderHit hit) {
    if (hit.rigidbody == null || hit.rigidbody.isKinematic) return;
    var cube = hit.rigidbody.GetComponent<PickupCube>(); if (cube == null) return;
    Vector3 v = ComputePushVelocity(hit);              // 优先用 CC 速度，否则用 moveDirection
    if (IsServer) cube.ApplyPush(v);                   // 主机玩家：直接施加
    else if (IsOwner) RelayPush(cube, v);              // 客户端玩家：0.08s 节流中继给服务器
}
```
- CharacterController **本身不会推动刚体**，必须显式施加推力；
- 客户端玩家没有箱子所有权 → `[ServerRpc] PushCubeServerRpc` 里服务器做**软校验**：发送者必须真实存在、距箱子 ≤1.6m、速度在 0.01~100 之间，才 `cube.ApplyPush(v)`。
- ⚠️ 曾踩的坑（写在 `Docs/Level3-双生仓库-设计.md`）：这里若写成 `if (!IsServer) return;`，**只有主机玩家推得动箱子**。

**（5）输入抑制**：`Update` 开头 `if (ChatSystem.IsChatOpen) return;` —— 聊天打开时玩家不动（否则打字触发 WASD 走路）。

### 3.3 `ChatNetwork`：两行代码的聊天中继 (NetworkBehaviour)

```csharp
[ServerRpc(RequireOwnership = false)]
public void SendChatServerRpc(string sender, string message, ServerRpcParams rpcParams = default)
    => ReceiveChatClientRpc(rpcParams.Receive.SenderClientId, sender, message);   // 服务器转发

[ClientRpc]
void ReceiveChatClientRpc(ulong senderId, string sender, string message)
    => ChatSystem.Instance?.OnMessageReceived(senderId, sender, message);
```
**为什么需要这条 SenderId？** 因为中继的是**字符串内容**，接收端无法从 `NetworkMessage` 反查是谁发的；服务器顺手把 `SenderClientId` 塞进广播参数，接收端便能按玩家着色（P1 琥珀 / P2 灰蓝）。这是"服务器数据补全"的小范例。

### 3.4 断线对账链（联机健壮性的核心设计）

```
OnClientDisconnectCallback
├ 客户端侧（!IsServer）：自己掉线 → ReturnToLobbyAfterDisconnect → ExitRoom() → 回大厅
└ 服务器侧（clientId != 本机）：
     GameHUD.ShowToast("P2 已断开连接")
     LevelManager.OnPlayerDisconnected(clientId)      // 清空该玩家的出口状态
     foreach (NpcDialogue npc) npc.OnPlayerDisconnected(clientId)  // 取消待确认的任务
```

**为什么要"对账"？** 因为**玩家对象销毁不会触发 `OnTriggerExit`** —— 任何基于 Trigger 计数的状态（出口、压力板）都可能永久卡死，把谜题锁死。所以：

- `LevelExit` 走 Trigger，但**对账兜底**在 `LevelManager.OnPlayerDisconnected`；
- `PressurePlate` 干脆**不用 Trigger**，改成服务器每 0.2s 重叠查询（见 §5.2），从设计上消除卡死概率。

这条"Trigger 计数 + 断线对账 / 或改用轮询"是很好的联机健壮性论点。

### 3.5 `EchoTester`（TCP 3001）

- 一个 UI 工具脚本：连 TCP 3001 → 收欢迎语 → 发 3 条（`Test1` / `Unity Echo` / `exit`）→ 收显式回显 → 断开，全程把结果打进 `_outputText`（带 `<color>` 标签）。
- 用 `System.Threading.Thread` + `BeginConnect(...).AsyncWaitHandle.WaitOne(5000)` 做**可超时的连接**，避免主线程卡死；接收用协程轮询 `stream.DataAvailable`。
- 用途：**跨设备连通性排查**（防火墙 / 端口 / 公网可达性）。与游戏链路无关，属于"工程自检工具"。
- 服务端对应 `server.js` 的 `net.createServer` Echo 服务（收到 `exit` 就 `socket.end()`）。
  > ⚠️ 静态核验发现：当前仓库的 `server/server.js` 调用了 `net.createServer`（第 54 行）但**文件内没有 `const net = require('net')`**，按此版本启动会在加载阶段抛 `ReferenceError: net is not defined`。线上实例可正常登录说明部署版本与仓库不一致——建议把该 require 补上（属于 5 分钟修复项）。

## 4. NPC 交互与任务选择模块

### 4.1 `NpcDialogue`：一个脚本 = 一个 NPC = 一个任务

**配置即关卡绑定**（每个 NPC 在场景里填 4 个字段就完成接线）：

| NPC | `_missionId` | `_levelSceneName` | `_levelTitle` |
|---|---|---|---|
| 大厅/NPC | 1 | `Level1` | 第一关：消失的钥匙 |
| 大厅/NPC2 | 2 | `Level2` | 第二关：文字狱 |
| 大厅/NPC3 | 3 | `Level3` | 第三关：双生仓库 |

**对话流程（纯本地 → 只影响 P1 的 UI）**：`Update` 检测距 NPC ≤ `_interactRange` 且未在对话 → 显示 `_interactHint`（世界空间 TMP）→ 按 **E** → `StartDialogue()` → 每按一次 NextButton `_dialogueIndex++` → 台词放完 `ShowMissionSelect()`。

**任务确认是双人协议（本模块的精华），用两个 NetworkVariable 当状态机**：

```
_selectedMission : int   // -1 未选（默认） / 1..3 已选任务
_confirmState    : int   // 0 无 / 1 等待 P2 确认 / 2 已确认 / 3 已拒绝
```

```
P1 点"接受任务" → SelectMissionServerRpc(missionId)                    [Client→Server]
       服务器：_selectedMission = id; _confirmState = 1
       广播：OnMissionSelected(服务器隐藏选单) / OnMissionSelected(P2 弹出确认窗)
       服务器：_confirmState==1 → 启动 ConfirmTimeout 协程（30s 后若仍为 1 → 置 0）

P2 点确认/拒绝 → ConfirmMissionServerRpc(bool)                          [Client→Server]
       服务器：_confirmState = 2 或 3
   == 2 → 双方关面板；服务器 GameManager.LoadLevel(_levelSceneName, _levelTitle)
   == 3 → 服务器 _selectedMission = -1、_inDialogue=false，Toast"P2 拒绝了任务，请重新与NPC交互"
   == 0 → 超时/掉线：双方关面板；服务器回选单，Toast"任务确认已取消"
```

**三个并发/边界处理（点名讲）**：
1. **只有 P1 能对话**：`Update` 开头 `if (!IsServer) return;` —— Host 的 clientId 恒为 0，等价于"只有 P1 可交互"；非服务器上 `_interactHint` 直接隐藏。
2. **单流程互斥**：静态列表 `_instances` + `AnyMissionPending()` —— 三个 NPC 的对话画布都是屏幕空间 UI，会互相重叠，因此**全局只允许一个任务流程进行**；`IsNearestNpc(dist)` 再解决"两个 NPC 站得近，E 键该给谁"。
3. **掉线取消**：`OnPlayerDisconnected` 由 `GameManager` 调用，`_confirmState==1 → 0`，避免 P2 掉线后 P1 卡在等待。

**一个 UI 生命周期坑（已修）**：NPC 的 `DialogueCanvas` 在场景里是 **inactive** 的，如果只在 `Awake` 里 `SetActive(false)` 子面板，父画布不激活则面板永远不可见、也收不到点击。代码里显式激活父画布：
```csharp
if (_dialoguePanel != null && _dialoguePanel.transform.parent != null)
    _dialoguePanel.transform.parent.gameObject.SetActive(true);
```

## 5. 谜题判定与关卡流程模块

### 5.1 关卡流程：`LevelManager` + `LevelExit`

**`LevelManager`（每个关卡场景一个，NetworkBehaviour 单例）**

```csharp
NetworkVariable<bool> _p1InExit, _p2InExit;                 // 服务器写，全员读
public bool IsComplete => _p1InExit.Value && _p2InExit.Value;
[SerializeField] string _levelName, _objectiveText;         // 每关在场景里配：关卡名 + 目标
[SerializeField] Vector3 _p1Spawn, _p2Spawn;                // 每关出生点
```

- `OnNetworkSpawn`：订阅两个 `OnValueChanged` → **服务器传送双方到本关出生点**（因为玩家对象跨场景保留，见 §3.1）→ 设置 HUD 关卡名 → `UpdateStatus()`。
- `OnPlayerInExit(playerNumber, inExit)`：仅服务器可写（`if (!IsServer) return;`）。
- `OnExitChanged` → `UpdateStatus()` + 两者都在 → `ShowComplete()`。
- `UpdateStatus()`：更新场景内 `_statusText`（TMP 富文本，"✓ / …"）+ `GameHUD.SetHint(StatusHint)`。注释里留了一个 TMP 细节：**TMP 不认颜色名 `gray`，要用 `grey` 或十六进制**，否则标签会当纯文本渲染。
- `ShowComplete()`：`_completeShown` 幂等 → 完成面板 + `GameHUD.ShowPuzzleComplete` + `PlaySfx("PuzzleComplete")` → 服务器启动 `ReturnToNpcRoutine()`。
- `ReturnToNpcRoutine()`：for 5→1，每秒 `UpdateCountdownClientRpc(i)`（全客户端 Toast "N 秒后返回 NPC 房…"）→ `GameManager.LoadLevel("大厅")`。

**`LevelExit`（触发器型，两种范式之一）**

```csharp
void OnTriggerEnter(Collider other) {
    if (!IsServer) return;                                   // 只有服务器检测
    var player = other.GetComponent<PlayerMove>(); if (player == null) return;
    int playerNum = (int)player.OwnerClientId;
    if (playerNum != _playerNumber) return;                  // 这是 P1 的出口就只能 P1 进
    LevelManager.Instance?.OnPlayerInExit(_playerNumber, true);
}
```
"**人在哪个出口**用 `OwnerClientId` 判定，而不是 `gameObject.name`/`tag`" —— 服务器权威下的正确身份来源。`Exit_P1`/`Exit_P2` 场景里各一个，`_playerNumber` 分别 0/1。

### 5.2 机关：`PressurePlate` + `LockedDoor`（Level3 的核心，也是论文"协作机关"一节的正面案例）

**`PressurePlate` —— 为什么不用 Trigger，而用"服务器重叠查询"？**

```csharp
void Update() {                                  // 仅服务器
    _verifyTimer += Time.deltaTime;
    if (_verifyTimer < _verifyInterval /*0.2s*/) return;
    _verifyTimer = 0f;
    RefreshOccupants();
}

void RefreshOccupants() {
    Bounds b = col.bounds;
    int n = Physics.OverlapBoxNonAlloc(b.center + up*0.05f, b.extents + (0.06,0.35,0.06),
                                       _overlapBuffer, Quaternion.identity, ~0, QueryTriggerInteraction.Collide);
    _fresh.Clear();
    for (i<n) if (TryGetOccupantId(buf[i], out ulong id)) _fresh.Add(id);
    if (_fresh.SetEquals(_occupants)) return;     // 集合没变 → 不写 NetworkVariable（省带宽）
    _occupants.Clear(); foreach (id in _fresh) _occupants.Add(id);
    RefreshPressed();                             // Count>0 → _isPressed.Value = true
}
```
三个设计理由（答辩可以直接背）：
1. **瞬移/静止的 CharacterController 不可靠触发 Trigger**（服务器的 `OnTriggerEnter` 可能漏），**轮询物理重叠是幂等的**，不会漏也不会重复计数；
2. 用 **`HashSet<ulong>`（NetworkObjectId 集合）** 而不是计数器 → 重复事件不会让计数错乱，**比较用 `SetEquals`** → 无变化时不写 NetworkVariable；
3. **玩家掉线/物体销毁 = 从集合里自然消失** → 压力板绝不会永久卡住把谜题锁死（这正是 §3.4 提到的"Trigger 计数卡死"问题的根治方案）。

`TryGetOccupantId` 用 `GetComponentInParent<PlayerMove>()` / `<PickupCube>()`（**碰撞体常挂在子物体上**）+ `GetComponentInParent<NetworkObject>()` 取网络 ID。支持**用箱子压板**（`_acceptPickupCubes`）——这是"以物代人"的合作解法基础。

`OnPressedChanged`（全员）：改材质颜色（绿=压下 / 灰=弹起）+ `PlaySfxAt("PlatePress"/"PlateRelease")`。

**`LockedDoor` —— 轮询型（另一种范式）**

```csharp
void Update() {
    if (IsServer) {                                   // 服务器每帧评估接线
        bool shouldOpen = EvaluatePlates();
        if (shouldOpen != _isOpen.Value) _isOpen.Value = shouldOpen;
    }
    // 所有客户端做同样的平滑动画（只读 _isOpen）
    transform.localPosition = Vector3.Lerp(transform.localPosition,
        _isOpen.Value ? _openPos : _closedPos, _animSpeed * Time.deltaTime);
}

bool EvaluatePlates() {
    if (_requireAllPlates) {                          // AND 模式
        for each plate: if (plate == null || !plate.IsPressed) return false;   // 未接线=不可满足
        return true;
    }
    for each plate: if (plate != null && plate.IsPressed) return true;         // OR 模式
    return false;
}
```

| 参数 | 含义 |
|---|---|
| `_requireAllPlates = false` | **任一**板被压即开（OR）→ 实现"一人踩板、对面开门"的看门人机制 |
| `_requireAllPlates = true` | **所有**板同时被压才开（AND）→ 实现"两人/两重物同时"的收尾机制 |
| `_plates[]` | **允许指向对面走廊的压力板** → "你需要的门只能由同伴打开"，这是第三关的设计灵魂 |
| `_displayName` / `_announceState` | 状态变化时 HUD Toast"左厅第 1 道闸门 已开启" → 让玩家知道"对面走廊的门开了" |
| `_openOffset` | 开门位移（脚本默认 `(0,4,0)` 上移；第三关场景配成 `(0,-3.2,0)` 下沉）；`UpdateDoorVisual` 同步开关 Collider |

**门与板的关系是"拉/轮询"而非"推/事件"**：`PressurePlate` 只管自己 `IsPressed`，`LockedDoor` 每帧 `EvaluatePlates()` 读它。好处：**接线（谁控制谁）完全在场景里配置**，加一块板/一扇门不用改代码，也不用维护订阅关系（无内存泄漏风险）。代价是每帧一次 N 次比较（可忽略）。

> 注意与旧代码（`Scripts/Puzzle/`）的区别：旧实现是"压力板主动 `linkedDoors` 推 `SetOpen`"（推模式），新实现是"门拉取板状态"（拉模式）。**两种范式在同一项目里都存在**，可对比讲优缺点。

**第三关《双生仓库》接线表（`Docs/Level3-双生仓库-设计.md`，场景已实现）**

| 闸门 | 条件 | 设计意图 |
|---|---|---|
| 闸门_L1 | OR(压力板_R1, 压力板_R2) | 右厅的板开左厅的门 → **看门人** |
| 闸门_R1 | OR(压力板_L1) | 左厅的板开右厅的门 |
| 闸门_L2 / R2 | OR(压力板_L2b) | 箱子压住即常开 |
| 闸门_L3 | **AND**(压力板_L3b, 压力板_R3b) | **同时操作**收尾 |
| 闸门_R3 | OR(压力板_L3b) | 箱子压住即常开 |

配套的**关键不变量**（Scene/Physics 层，答辩可能被追问）：
- 可搬运箱必须在 **`Carryable(9)`** 层，传递窗屏障在 **`CoopChute(10)`** 层，且 `Physics.IgnoreLayerCollision(10, 9, true)`（已写入 `ProjectSettings/DynamicsManager.asset`）→ 箱子能过、人过不去；
- 场景内 NetworkObject 是"场景放置对象"，随场景加载 spawn，**不需要注册进 `DefaultNetworkPrefabs`**；
- 移动/传送玩家一律走 `PlayerMove.ServerTeleport`。

### 5.3 第一关《消失的钥匙》：调查式谜题（另一种谜题范式）

第一关不是压力板，而是"**翻遍房间 → 揭示真相**"，实现用了**接口注册表 + RPC 路由**：

**（1）`IRoomInteractable` 接口 —— 统一一切可交互物**

```csharp
public interface IRoomInteractable {
    int TargetId { get; }  Transform InteractTransform { get; }  float InteractRange { get; }
    string DisplayName { get; }  string InteractVerb { get; }  bool IsAvailable { get; }
    string SearchKey { get; }                       // 非空 = 计入调查进度
    string AdvanceLine();                            // 服务器：取当前台词并推进（末句重复）
    void ShowInteractResult(ulong senderId, string line);   // 客户端：本地展示
    void RequestInteract();                          // 客户端：发起请求
}
```

两个实现：
- `InvestigationTarget`（柜子 / 壁画 / 墙上文字 / 门前告示 / 场景 NPC，Level1 里 5 个）：台词数组**渐进播放、末句重复**；`_requiredForHint` 标记是否计入"翻遍房间"；`_speakerPrefix` 非空则以 NPC 名发言，否则以 "Pn" 叙述。
- `KeyPuzzleDoor`（大门）：不计数（`SearchKey = ""`），台词由管理器按"试开次数 / 是否已揭示"决定。

**（2）注册表 + ID 路由（`KeyPuzzleManager`）**

```csharp
public static readonly List<IRoomInteractable> Registry = new();
public static readonly Dictionary<int, IRoomInteractable> ById = new();

void OnEnable()  { Registry.Add(this); ById[_targetId] = this; }   // 交互物自注册
void OnDisable() { Registry.Remove(this); if (ById[id] is this) ById.Remove(id); }
```
- **"对象自注册到管理器"** 让管理器无需在场景里逐个拖引用；
- **`ById`** 是为了让 RPC 只传一个 `int targetId`（NetworkVariable/RPC 不能序列化接口引用）→ 收到 ID 再查表还原对象。这是很实用的序列化/引用解耦技巧。

**（3）E 键交互中枢（`KeyPuzzleManager.Update`）**
```
若 聊天打开 / 暂停 → 隐藏提示并 return
找本地玩家 → 遍历 Registry → 剔除已销毁项（t is Object uo && uo == null）
       → 取"在范围内且最近"的那个 → 世界空间 TMP 提示 "按 E 调查{名字}"
       → 按 E → best.RequestInteract()
```
提示用 `Camera.main` 做 **Billboard（朝向相机）**，Y 位置取目标 Renderer 上面 0.35m（`rend.bounds.max.y`），保证不同高的柜子/壁画都能正确显示。

**（4）请求—校验—广播闭环**
```csharp
[ServerRpc(RequireOwnership = false)]
void InvestigateServerRpc(int targetId, ServerRpcParams rpcParams = default) {
    if (!ById.TryGetValue(targetId, out var target)) return;
    if (!ValidateSender(target, rpcParams)) return;              // 距离 ≤ InteractRange*2（容忍延迟）
    string line = target.AdvanceLine();                          // 服务器推进进度（唯一可信）
    if (!string.IsNullOrEmpty(target.SearchKey)) RegisterSearch(target.SearchKey);
    ShowInvestigationClientRpc(targetId, rpcParams.Receive.SenderClientId, line);   // 全员看到
}
```
- **进度（台词下标 / 已搜索集合）只存在服务器**，客户端只是展示 → 无法靠改本地伪造进度；
- 台词广播给**所有人**（协作游戏里"队友看到你翻了什么"很重要），发言者用 `SenderClientId` 还原成 "P1/P2"。

**（5）谜底解锁（两段式设计，这是第一关的"谜题内核"）**
```csharp
void RegisterSearch(string key) {
    if (!_searchedKeys.Add(key)) return;                                  // HashSet 幂等
    if (_searchedKeys.Count >= RequiredTargetCount() && !_hintRevealed.Value)
        _hintRevealed.Value = true;                                       // 全员同步 → 墙上金字出现
}
```
- `RequiredTargetCount()` = 统计 `Registry` 里 `IsRequiredForHint == true` 的 `InvestigationTarget` 个数 → **进度阈值跟着场景自动变**，加减调查物不用改代码。
- 揭示时：`WorldDialogueBox.Show("", "……大门上方浮现出一行金字——「钥匙不在房间里。」")` + `PlaySfx("PortalEnter")`，并 `SetActive(true)` 墙上的 `_wallHintText`。

**（6）门的"假锁"逻辑（`DoorInteractServerRpc`）**
```
已开 → AlreadyOpenLine（"门已经开了，快走吧。"）
已揭示谜底 → _doorOpened = true + RevealLine（"锁孔里根本没有锁芯，这把'锁'只是画上去的！"）
未揭示 → 依次播放 _lockedLines[0..n-1]，_doorTryCount 递进到最后一档后不再变
```
`KeyPuzzleDoor` 本体是普通 MonoBehaviour（状态由管理器持有，**Poll 模式**）：在 `Update` 里比对 `KeyPuzzleManager.DoorOpened`，变化时触发 `OnOpenedTransition`（关 Collider + `DoorOpen` 音效），未开完时按 **绕铰链的参数化旋转**动画：
```csharp
float angle = _openAngle * _openT;                       // _openT: 0→1
Quaternion delta = Quaternion.AngleAxis(angle, Vector3.up);
transform.SetPositionAndRotation(_hingePoint + delta * (_closedPos - _hingePoint), delta * _closedRot);
```
**所有客户端各自算同一个解析式动画**（只依赖同步来的布尔状态），不需要同步角度 → 省带宽且必定一致。

### 5.4 可搬运箱 `PickupCube`（跨关卡的通用协作道具）

```csharp
[RequireComponent(typeof(Rigidbody))] [RequireComponent(typeof(NetworkTransform))]
```
| 机制 | 实现 |
|---|---|
| 归属 | `_isHeld`(bool) + `_holderId`(ulong) 两个 NetworkVariable |
| 拾取 | 客户端按 E → `TryPickupServerRpc`（`RequireOwnership=false`）→ 服务器校验**距离 ≤ pickupRange** 后才置位 |
| 搬运 | **服务器**在 `Update` 里把方块 Lerp 到 `持有者.forward * holdDistance + up * holdHeight`，位置经 **`NetworkTransform` 组件**自动复制给所有人（不再每帧发 RPC） |
| 放下 | `DropServerRpc` 校验"确实是你持有的" → 释放 + 沿视线给 `dropForce` 初速 |
| 状态反馈 | `OnHeldChanged`：`isKinematic = held`、`useGravity = !held` + `CubePickup/CubeDrop` 音效 |
| 推箱 | `ApplyPush(horizontalVelocity)`（**唯一入口**，由 `PlayerMove` 主机直调或客户端中继调用）；`Rigidbody.drag = pushDrag` 提供阻力 |
| 音效/输入 | `Input.GetKeyDown(E)` 前检查 `!ChatSystem.IsChatOpen && !GameHUD.IsPaused` |

**为什么位置用 `NetworkTransform` 而不是 NetworkVariable？** 因为是高频连续变化量，NGO 内置组件已做了插值/压缩/dirty 判定，**不要自己造轮子**；而"是否被持有 / 被谁持有"是低频离散状态，用 NetworkVariable 更划算。→ **按数据特征选择同步方式**，这是很好的答辩论点。

> 注意 `PickupCube` 的 E 键与 `KeyPuzzleManager` 的 E 键**可能在同一帧抢输入**（Level1 无箱子，Level3 无调查物，所以当前不冲突；但这是设计上要留意的点）。

### 5.6 关卡辅助表现

- **`OcclusionWallHider`**：当本地玩家越过墙平面（`z > _wallZ`）时**关闭出口墙体 Renderer**，否则玩家穿过出口通道时会被墙挡住视野；回程超过 `_wallZ - _showOffset`（0.5 回差）再显示。**回差（hysteresis）是防闪烁的标准做法**。

## 6. UI 与聊天模块

### 6.1 `UIManager`：菜单状态的唯一开关

```csharp
void Start() {
    _login.OnLoginSuccess += OnLoginSuccess;     // 登录成功 → ShowRoom
    _room.OnLogout += ShowLogin;                 // 登出 → ShowLogin
    _room.OnEnterGame += TransitionToGame;       // 进游戏 → 淡出菜单
    if (ApiClient.IsLoggedIn) ShowRoom(); else ShowLogin();   // 自动登录分支
    AudioManager.Instance?.PlayBgm("MenuBGM");
}
```
- 三种入口：`ShowLogin`（登录）/ `ShowRoom`（大厅）/ `ShowLobby`（从游戏退回，语义化命名，行为同 ShowRoom）；
- `TransitionToGame` 用 `CanvasGroup.alpha` 做 0.5s 淡出后 `SetActive(false)` → **用 alpha 淡出而不是直接隐藏**，避免菜单"啪"地消失；
- `_menuGroup.alpha = 1f` 在每次显示时复位（否则第二次进菜单会是透明的）。

### 6.2 `GameHUD`：游戏内的信息与设置中枢

| 功能 | 键位 | 实现要点 |
|---|---|---|
| 关卡名 / 目标提示 | — | `SetPuzzleName` / `SetHint`（`_hintBase` 缓存基准文本） |
| 临时消息 Toast | — | `ShowToast(msg, dur)`：覆盖 hint 文本，`_toastRoutine` 到期还原 `_hintBase`（**可打断**：新的 Toast 会 `StopCoroutine` 旧的） |
| 通关覆盖层 | — | `ShowPuzzleComplete` + `CanvasGroup` 渐入；`HidePuzzleComplete` |
| 暂停菜单 | **ESC** | `OnPause/OnResume`，并置静态 `IsPaused` 供其他脚本查询 |
| 设置面板 | 暂停菜单内 | 分辨率下拉（`Screen.resolutions` + `refreshRateRatio`）、全屏开关、三路音量滑块（与 HUD 内三个滑块**双向同步**） |
| 隐藏 HUD | **Tab** | 切 `_hudCanvasGroup.alpha` 并同步 `blocksRaycasts` |
| FPS | — | 每 0.5s 统计一次，颜色按 ≥50 绿 / ≥30 黄 / 否则红（答辩演示自查性能用） |

两个"踩出来的"细节值得讲：
1. `Start()` 里强制 `_hudCanvasGroup.blocksRaycasts = true` —— 场景里为了让 3D 世界可点，CanvasGroup 被设成了不接收射线，结果**暂停菜单按钮和聊天输入框都点不到**；HUD 自己接管射线。
2. 监听器用 `RemoveAllListeners()` + `AddListener()`（`RegisterListeners/UnregisterListeners` 在 `OnEnable/OnDisable` 配对）→ **重复进场景不会累积回调**。

### 6.3 `ChatSystem`：运行时构建 UI 的 LOL 式聊天

| 行为 | 键 | 说明 |
|---|---|---|
| 打开输入 | **T** | 打开前检查 `GameHUD.IsPaused`；`ActivateInputField()` + `EventSystem.SetSelectedGameObject` 才能拿到键盘焦点 |
| 发送 | **Enter** | `onEndEdit` 里判断 `GetKeyDown(Return/KeypadEnter)`；`IsChatOpen` 置位 |
| 取消 | **Esc** | 关闭并清空输入 |
| 置顶历史 | **Y** | `_historyPinned` 切换 |
| 系统消息 | — | `ShowSystemMessage`，黄色，不走网络 |

设计要点：
- 消息上限 **8 条 / 120 字 / 10 秒后淡出**（`MaxMessages` / `MaxMessageLength` / `MessageVisibleDuration`），`CanvasGroup.alpha` 用 `Mathf.MoveTowards` 做淡入淡出；
- **按玩家着色**：`ColorForClient(0)` 琥珀、其余灰蓝（同一套配色在预览行也在用）；
- **打字实时预览**：`onValueChanged → UpdatePreview`，在消息列表末行显示半透明的"我正在输入的内容"；
- **UI 全部代码构建**（`BuildUI` / `BuildInputField`）：`ChatPanel`(CanvasGroup+Image) → `Messages`(VerticalLayoutGroup + ContentSizeFitter) → `Preview` 行 → `ChatInput` → `TMP_InputField`（手工接 `textViewport` / `textComponent` / `placeholder`）。行高用 `GetPreferredValues(text, 380f, 0).y + 4f` 动态计算 → **长消息换行不会压到下一行**。这样做的原因：**HUD 画布是常驻的，聊天面板代码生成可以免去在各场景重复搭建/引用**；
- 静态 `IsChatOpen` 供 `PlayerMove` / `NpcDialogue` / `KeyPuzzleManager` / `PickupCube` 抑制输入（**集中式输入仲裁**）。

### 6.4 `LoadingScreen`：诚实的"化妆进度条"

```csharp
BeginRoutine(title): 随机选一条 tip → 淡入 → 进度爬向 90%
                      （<60% 速度 0.35，之后 0.12 → 越接近越慢）
CompleteRoutine():   直接置 100% → 停 0.35s → 淡出 → SetActive(false)
```
- **进度是化妆的**：Netcode 不暴露场景加载进度，所以"等到 90% 就卡住，等 `OnLoadComplete` 一到立刻 100%"。**这一点必须主动说明**，否则评委问"进度条真的反映加载进度吗"会很尴尬；
- 注释里记录了坑：协程不能在 inactive 的 GameObject 上启动，所以 `Begin` 里先 `SetActive(true)` 再 `StartCoroutine`（对象在 `Awake` 里自禁用）。

### 6.5 `WorldDialogueBox`：世界交互台词框

- 常驻在 `GameHUDCanvas` 下，**用 `CanvasGroup.alpha` 控制显隐而不是 `SetActive(false)`**，原因写在注释里：保持 GameObject 激活才能让 `Awake` 在场景加载时一定执行、静态 `Instance` 一定有效；
- `Show(speaker, text, duration)` 静态入口 → 有 Instance 就走对话框（`_nameplate` 空说话人时隐藏 → 旁白模式），没有就降级为 `GameHUD.ShowToast`（**优雅降级**）；
- 渐入 0.15s / 停留 `duration` / 渐出 0.3s，用 `Time.unscaledDeltaTime` + `WaitForSecondsRealtime`（**暂停时也能正常计时**）。

## 7. 表现层：音频 / 迷雾 / 像素化

### 7.1 `AudioManager`：零音频资产的程序化音频系统

**架构**：单例 + `DontDestroyOnLoad`；2 个 BGM `AudioSource`（交叉淡入淡出）+ 16 个 SFX `AudioSource` 池（默认 `spatialBlend = 1` 3D、`Logarithmic` 衰减、`maxDistance=30`）。

**调用 API（全项目统一，字符串名寻址）**
```csharp
AudioManager.Instance.PlaySfx("UIClick");                     // 2D
AudioManager.Instance.PlaySfxAt(pos, "Footstep", 0.1f);       // 3D + 随机音高
AudioManager.Instance.PlayBgm("ChamberBGM");                  // 交叉淡入淡出（1.5s）
```

**clip 表（`GenerateAllClips`，`Awake` 中一次性合成）**

| 名称 | 用途 | 名称 | 用途 |
|---|---|---|---|
| `PortalShoot` / `PortalEnter` | 传送门（当前禁用模块） | `Footstep` / `Footstep2` | 脚步（同一波形，⚠️ 重复） |
| `PlatePress` / `PlateRelease` | 压力板 | `UIClick` | 所有按钮 |
| `DoorOpen` / `DoorClose` | 闸门 / 大门 | `Connect` | 连接成功 |
| `CubePickup` / `CubeDrop` | 箱子（也用于调查交互、锁门敲击） | `ZoneEnter` / `PuzzleComplete` | 出口 / 通关（C-E-G-C 上行旋律） |
| `LaserActivate/Deactivate` | 激光（旧模块） | `ChamberBGM`(16s A 小调) / `MenuBGM`(12s C 大调) | 关卡 / 菜单 |

**合成原理（论文"音频设计"一节的材料）**：全部基于 `AudioClip.Create` + `SetData` 直接写 PCM 采样：
- **噪声类**（脚步、撞击）：`Random.Range(-1,1)` 乘指数包络 `exp(-t*k)`；
- **音调类**（UI、连接）：正弦 + 指数包络，频率用 `Mathf.Lerp` 做上/下滑音；
- **机械类**（门）：低频正弦（60~80Hz 电机）+ 噪声（摩擦）+ `Mathf.SmoothStep` 包络；
- **旋律类**（通关）：音高数组 `{523,659,784,1047}`（C-E-G-C），按 `t / noteDur` 选音，每个音独立 ADSR（`exp(-noteT*3) * (1-exp(-noteT*50))`），叠一个二次谐波（`*2` 频率，0.15 增益）增加"亮度"；
- **BGM**：分层叠加 —— 低音线（A/A/F/G 每 4 拍换）+ 琶音（A 小调音阶，0.5 拍一次）+ 持续 pad（110/165/220Hz 三音）+ 极低幅"氛围噪声"。

> 优点：**零外部资产**（体积小、无版权问题、可参数化调音）。缺点：`Awake` 里同步合成约 130 万采样点（16s BGM 单独就是 70 万），启动有一次性开销；`CrossfadeBgm` 若被连续调用会有两个协程抢同一对 AudioSource 的可重入风险。

### 7.2 `FogSimulation` + `FogObstacle`：ComputeShader 迷雾

**目标**：给第一关做"探查感"的 2D 雾（GameObject 是一个贴在地面的 Mesh），每帧算一张密度场 RenderTexture 给 `fogMaterial._DensityTex`。

```
Start():
  ① ResolveLocalPlayer() —— 序列化的 player 引用指向的是**预制体资产**（不在任何场景里），
     所以要先判断 player.gameObject.scene.IsValid()，无效则改用 SpawnManager.GetLocalPlayerObject()
  ② 若 |玩家.x - 本雾.x| > areaSize → 说明本地玩家在"另一条时间线" → enabled=false + 隐藏 MeshRenderer
  ③ 找 CSMain kernel、groups = ceil(res/8)
  ④ 建两张 RFloat RenderTexture（双缓冲，enableRandomWrite）
  ⑤ InitializeObstacles()：遍历场景 FogObstacle → 世界坐标转 UV + 半径归一化 → ComputeBuffer
  ⑥ 预热 90 步 Step(0.1f) —— 否则开局是一张空（无雾）纹理

Update(): Step(Time.deltaTime)

Step(dt):
  计算玩家 UV 位置与 UV 速度（上一帧位置差 / dt）
  设置 uniform：_Resolution/_PlayerPos/_PlayerVel/_PlayerRadius/_Wind/_Push/_Swirl/_Regrow/t/dt
  SetTexture(Source=density[current], Result=density[next]) → Dispatch → fogMaterial._DensityTex = density[next]
  current = next
```
设计要点：
- **每个客户端只模拟包裹自己玩家的那一份雾**（`distX > areaSize` 就自禁用）→ 两台机器各算各的、负担减半，视觉上各自只看自己那侧；
- 双缓冲 ping-pong（`current/next`）避免同帧读写同一张 RT；
- 障碍物一次性上传到 `ComputeBuffer`（CPU 侧只做一次世界→UV 转换）；
- `WorldToUv` 把 `x/z` 映射到 0~1，`/areaSize + 0.5f` 即"以雾中心为原点"。

### 7.3 `PixelationFeature`：HD2D 的像素化后处理（**当前失效，必须如实讲**）

写法本身是正确的 URP 14 风格（`ScriptableRendererFeature` + `RTHandle` + `Blitter.BlitCameraTexture` 两趟：先渲到临时 RT 再回相机目标），但**当前完全不生效**，三个原因：

| # | 问题 | 修法 |
|---|---|---|
| ① | `PixelationFeature` **没有被挂到任何 URP Renderer**（三档 Renderer 资产里都没有它的实例） | 在 Renderer 资产的 Renderer Features 列表 Add 一个 |
| ② | `Pixelation.shader` 还是旧式顶点输入（`POSITION`/`TEXCOORD0`），而 URP 14 `Blitter` 用 `DrawProcedural` **不绑顶点缓冲** | 改用 `GetFullScreenTriangleVertexPosition(input.vertexID)` |
| ③ | 片元采样 `_MainTex`，而 Blitter 绑定的是 `_BlitTexture`（`_MainTex_TexelSize` 恒 0 → 除零 NaN） | 改采样 `_BlitTexture` |
| ④ | `Shader.Find("Hidden/Pixelation")` 在构建时可能被剔除（返回 null → Pass 直接 return） | 改 `[SerializeField] Shader` 引用或加入 Always Included Shaders |

> 答辩策略：主动说明"HD2D 的骨架（3D 场景 + 2D 像素精灵 + 俯角相机 + 三档 URP 质量）已实现，像素化后处理因 URP 14 Blitter 接口变更尚未接通，已定位到 4 个具体原因并给出修法" —— 这比声称"已实现"然后被现场看出来要好得多。

## 9. 设计模式与网络范式总结（论文/答辩可直接引用）

| # | 模式 / 范式 | 项目中的落点 |
|---|---|---|
| 1 | **单例（带 `OnDestroy` 清理）** | `GameManager` / `AudioManager` / `UIManager` / `GameHUD` / `ChatSystem` / `LoadingScreen` / `LevelManager` / `KeyPuzzleManager` / `WorldDialogueBox` |
| 2 | **服务器权威（Server-Authoritative）** | 所有关键状态（门、板、出口、任务确认、箱子归属）只由服务器写；客户端只发请求 |
| 3 | **状态同步三原语** | NetworkVariable（状态）/ ServerRpc（请求）/ ClientRpc（通知），见 §0.4 三条铁律 |
| 4 | **观察者（事件订阅）** | `OnValueChanged` 订阅-退订成对出现在 `OnNetworkSpawn/OnNetworkDespawn`；UI 侧用 C# `event`（`OnLoginSuccess` / `OnLogout` / `OnEnterGame`）解耦 |
| 5 | **接口 + 注册表（策略/插件的轻量版）** | `IRoomInteractable` + `Registry` / `ById` → 新增可交互物零改管理器 |
| 6 | **推 vs 拉（两种机关接线范式）** | 旧 `PressurePlate`→`PuzzleDoor.SetOpen`（推）；新 `LockedDoor` 每帧 `EvaluatePlates()`（拉） |
| 7 | **轮询替代 Trigger（健壮性）** | `PressurePlate` 用 `OverlapBoxNonAlloc` 每 0.2s 重建占位集合，天然免疫"对象销毁不触发 Exit" |
| 8 | **节流 / 阈值同步** | `PlayerMove` 0.1s + 0.1m 双条件；推箱中继 0.08s；压力板"集合无变化不写" |
| 9 | **定向 RPC** | `ServerTeleport` 用 `ClientRpcParams.TargetClientIds = { OwnerClientId }` 只通知 owner |
| 10 | **横切关注点集中** | `ApiClient` 统一鉴权 / 超时 / 401 兜底 / 错误抽取 |
| 11 | **前后端双层校验 + 服务端强制** | 登录注册参数、ServerRpc 的距离/速度软校验 |
| 12 | **优雅降级** | `WorldDialogueBox.Show` 无对话框时退化为 Toast；`RoomPanel` 空列表占位行；客户端手输 IP 直连（绕开后端） |
| 13 | **做旧兼容 / 幂等初始化** | `db.js` 的 `CREATE TABLE IF NOT EXISTS` + `INSERT OR IGNORE` 播种 + `last_activity` 列迁移 |

**一句话总结（可用于答辩开场）**：
> 项目采用"云服务器做账号与房间匹配、Netcode 做 P2P 联机、服务器权威做状态判定、客户端只做表现"的分层架构；代码上通过三类网络原语 + 单例常驻服务 + 接口注册表把 6 个功能模块解耦，全部数据（门、板、出口、任务）由服务器裁决，客户端无法伪造。

## 10. 已知问题与改进方向（**答辩追问预案**，务必先看这一节）

### 10.1 功能/内容
1. **第二关（Level2）不可通关**：只有 `LevelManager` + 1 扇 `LockedDoor`，没有 `LevelExit`、没有 `ChatNetwork`。→ 论文测试范围应限定为**主菜单、大厅、Level1、Level3**（与第 5 章草稿口径一致）。
2. **HD2D 像素化后处理未接通**（4 个具体原因，见 §7.3）。
3. **传送门系统未联网**（脚本完整、玩家预制体上已禁用）→ 定位为"第二/三关的储备素材"。
4. `Scripts/Puzzle/` 的激光/旧门/旧出口是死代码，且存在已知缺陷（每帧全场景 `FindObjectsByType`、发射器互相重置接收器、`_EMISSION` 不复位、Trigger 计数卡死）。→ **不要作为亮点讲**，如需启用需先重构。
5. **无掉落复活**：没有 y 下限检测，掉出世界只能 ESC 退房重开（第三关已封墙，风险低）。

### 10.2 联机健壮性
6. **位置完全由客户端上报**（`UpdateTransformServerRpc` 直接采信）→ 理论上可瞬移作弊。改进：服务器校验单帧位移 ≤ `speed*dt*安全系数`，超限回滚；`ServerTeleport` 走白名单豁免。（这条可以在论文"安全性设计"里写成"已知限制 + 改进方案"，很加分。）
7. 压力板已用重叠查询根治卡死；但**出口计数仍依赖 Trigger + 断线对账**（`LevelManager.OnPlayerDisconnected`），若玩家在出口内掉线再重连，需重新进入出口才会再次置真（可接受）。
8. `GameManager.OnClientConnected` 与 `RoomPanel.TransitionToGame` 会各播一次 `Connect` 音效（可能双响，小事）。

### 10.3 安全（后端）
9. **HTTP 明文**传输 + JWT **明文存 `PlayerPrefs`** → 生产环境应上 HTTPS（反向代理）+ 更安全的令牌存储；答辩时可讲"已知风险 + 演进方案"。
10. 注册重复用户名返回 **409 + "用户名已存在"** → 存在**账号枚举**风险；改进：统一返回模糊文案或改为邮箱验证。不过登录接口已经做了统一文案（"用户名或密码错误"），可以对比讲。
11. `bcrypt.hashSync` / `compareSync` **同步阻塞事件循环** → 高并发下应改异步版本 `bcrypt.hash/compare` 或 `worker_threads`。
12. `server/server.js` 缺 `const net = require('net')`（Echo 服务段），按仓库当前版本启动会抛 `ReferenceError`。

### 10.4 工程
13. **根目录缺 `.gitignore`**（`server/` 内有独立一份）→ `Library/`、`Temp/`、`Logs/`、`UserSettings/`、`*.csproj`、`*.sln`、`screenshots/`、`server/node_modules`、`server/data/` 都该忽略。
14. `Packages/manifest.json` 引用了**项目外**路径 `file:../.codely-cli/...`、`file:../.codely.packages/...` → 复制项目到别的机器会解析失败（答辩换机演示前务必确认，或改成项目内路径）。
15. **无 asmdef**（全部进 `Assembly-CSharp`）、**无测试文件**（Test Framework 已装但没用）、无自定义 Build Script（Build Settings：SampleScene(0) / 大厅(1) / Level1(2) / Level2(3) / Level3(4)）。
16. 三对易混目录：`Scripts` vs `Script`、`Materials` vs `Material`、`Prefabs` vs `Prefab`；中文目录名（`素材`、`迷雾`）与含空格的预制体名（`Player 1.prefab`）。
17. `AudioManager.Awake` 同步合成全部音频（一次性启动开销）；`Footstep2` 与 `Footstep` 是完全相同的重复 clip；`CrossfadeBgm` 可重入。
18. `ChatNetwork` 也存在于 `SampleScene`（菜单场景），菜单里发不出消息（无 HUD 之外的场景语义），属历史遗留，无害。

# 03 · 谜题玩法（联机化 + 双人协作扩展）

> 本模块把已有谜题系统打磨成「双人协作」核心体验，并给出可选的新谜题机制。核心原则：**所有谜题都要有「需要两人配合」的点**，否则就只是单人解谜的联机版，说服力不足。

---

## 提示词 3-A — 已有谜题机制盘点与联机化梳理

【目标工具】Codely
【使用时机】先做这一步，摸清家底
【提示词正文】

```
请先通读我工程里的谜题相关脚本（Assets/Scripts/Portal/ 与 Assets/Scripts/Puzzle/），帮我输出一份「机制清单 + 联机化改造建议」。要求：

1. 逐条列出每个机制（传送门、激光发射/接收/折射、压力板、拾取方块、机关门、出口）：
   - 当前单机行为
   - 哪些状态需要在联机时同步（NetworkVariable）
   - 哪些交互需要 ServerRpc
2. 标出当前是否存在「双人协作」设计；若没有，逐个机制给出「如何改造成需两人配合」的可行方案，例如：
   - 双压力板：必须两人同时踩两个压力板才能开门
   - 传送门配合：A 在甲处开橙门，B 在乙处开蓝门，相互传送
   - 激光接力：A 用折射镜改变激光方向，B 用方块阻挡/导通
   - 限时机关：开门后需一人持续踩住，另一人快速通过
3. 给出推荐优先级：哪些机制最容易做出「协作感」、最适合作为毕设展示核心玩法。

只做分析与建议，不要改代码。
```

【预期产出】一份机制清单与改造方案，明确「双压力板 + 传送门配合 + 激光接力」为三大核心协作玩法。据此选 1–2 个作为答辩演示关卡的核心。

---

## 提示词 3-B — 双压力板协作门（核心机制）

【目标工具】Codely
【使用时机】选好核心机制后
【提示词正文】

```
请实现「双人协作压力板门」机制，作为本作核心玩法。要求：

1. 场景中有两个压力板 PressurePlateA、PressurePlateB 与一扇 PuzzleDoor，两个压力板被同时踩下时门才打开，任一离开则门关闭。
2. 网络同步：用 NetworkVariable<bool> 分别保存两个压力板是否被压；门的状态由两个压力板的与运算得出；状态变化经服务器广播，所有客户端同步开关门与音效。
3. 单人无法同时踩两个板，天然需要两人协作；请在代码注释里写明这一设计意图。
4. 复用/改造现有 PressurePlate.cs、PuzzleDoor.cs（Assets/Scripts/Puzzle/ 下），不要破坏单板逻辑，做成可配置（板子数量、是否要求同时）。
5. 门开关接入 AudioManager 播音效（AudioManager.cs 已有，若没有对应音效接口请先补一个 PlayDoorSfx）。

请给出改造后的 PressurePlate.cs、PuzzleDoor.cs 及一个负责「多压力板组合逻辑」的脚本（如 PressureGate.cs）完整代码。
```

【预期产出】两人各踩一板门开，任一人离开门关，双方状态一致且有音效反馈。

## 提示词 3-C — 传送门联机化与双人配合

【目标工具】Codely
【使用时机】双压力板跑通后
【提示词正文】

```
请把现有传送门系统（Assets/Scripts/Portal/ 下）改造成联机可用，并强化双人配合。要求：

1. 传送门（橙门/蓝门）的创建与位置需在网络同步：A 开的门 B 也要能看到并穿过。用 NetworkObject + 服务器同步传送门的位置与朝向。
2. 传送枪（PortalGun）只有本地玩家能开自己的门，但门对所有人可见、可用（谁都能穿过）。
3. 双人配合点：设计上让「A 开的橙门 + B 开的蓝门」能形成跨空间的通路，例如 A 在甲处开橙门，B 在乙处开蓝门，实现两人在不同位置互相接应。
4. 处理传送的边界：正在被传送的对象（Player / PickupCube）如何避免无限传送/抖动；说明传送时 NetworkTransform 同步的处理。
5. 兼容点：刚体速度用 Rigidbody.velocity（不是 linearVelocity）。

请给出 PortalGun.cs、Portal.cs、PortalableObject.cs 的网络化改造代码，并说明传送门预制体需挂的组件。
```

【预期产出】双方能互相看到并使用对方的传送门，传送顺滑无抖动。

## 提示词 3-D — 激光折射接力（可选进阶）

【目标工具】Codely
【使用时机】想要更多玩法深度时
【提示词正文】

```
请把激光系统（LaserEmitter、LaserReceiver、LaserRedirector）改造成联机 + 协作玩法。要求：

1. 激光发射/折射/接收状态网络同步：LaserEmitter 是否通电、LaserRedirector 的旋转角、LaserReceiver 是否被命中。
2. 协作设计：折射镜需两人配合调整角度，或一人用方块挡住某路激光、另一人调整另一路，使激光同时命中两个接收器开门。
3. 激光可见性：所有客户端都能看到激光线（LineRenderer），且随折射同步更新。
4. 复用现有 LaserEmitter.cs、LaserReceiver.cs、LaserRedirector.cs，给出网络化改造代码，并把「多个接收器同时命中」的判据做成可配置。

请给出相关脚本的网络化版本及联机测试要点。
```

【预期产出】激光状态双方一致，可做出「双人调镜同时命中」的解谜体验。

## 提示词 3-E — 通关流程与出口上报

【目标工具】Codely
【使用时机】谜题做完后，接后端
【提示词正文】

```
请实现关卡通关流程并接后端上报。要求：

1. 复用现有 ExitZone.cs（出口），两名玩家都到达出口才算通关（协作收尾）；或设计成「A 开门，B 先过，A 再通过传送门会合」。
2. 通关后：主机记录本关用时（秒），调用 ApiClient 的 SaveProgress（保存 is_cleared、best_time_seconds）与 SubmitLeaderboard（更新排行榜）。
3. 通关画面：所有客户端同步显示「通关」提示与用时，并解锁下一关（进度存到 UserSession/后端）。
4. 说明：为什么只由主机上报（避免双人重复提交排行榜），以及非主机如何拿到通关结果。
5. 兼容点：不要用 Unity 6 API。

请给出改造后的 ExitZone.cs 与一个通关流程控制器（LevelClearController.cs）完整代码。
```

【预期产出】双人通关后，主机成功上报存档与排行榜，双方看到通关提示。

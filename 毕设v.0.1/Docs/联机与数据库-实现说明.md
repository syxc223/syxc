## 0 总体架构：两条独立通道

系统由两条互不干扰的链路组成：

| 通道 | 协议 / 端口 | 承载内容 | 实现位置 |
|---|---|---|---|
| **业务通道** | HTTP / **3000** | 注册登录、房间列表、建房、加房、离房 | `server/`（Node.js + Express + SQLite） |
| **游戏通道** | UDP / **7777** | 玩家位置、机关状态、谜题进度、聊天 | Netcode for GameObjects + UnityTransport |

设计上，云服务器只承担"**账号与房间介绍所**"职责：客户端通过 HTTP 完成身份认证与房间匹配，拿到房主的 IP 地址后，两名玩家通过 Netcode **点对点直连**，游戏运行期的所有数据不经过云服务器。

```
Unity 客户端 ──HTTP 3000──▶ Node.js + SQLite（users / rooms / room_members …）
      │                              │
      │◀──────── host_ip ────────────┘
      ▼
UDP 7777 直连（Host 同时是"服务器"与"1 号玩家"）
```

## 1 联机实现

### 1.1 组件配置与预制体注册

| 对象 | 挂载组件 | 作用 |
|---|---|---|
| `NetWorkManager`（场景常驻） | `NetworkManager` + `UnityTransport` | 网络会话总控与 UDP 传输层 |
| 玩家预制体 | `NetworkObject` + `NetworkTransform` + `PlayerMove` | 可被网络生成与同步的对象 |
| 关卡机关对象 | `NetworkObject` + 对应 `NetworkBehaviour` | 场景内网络对象，随场景加载自动 Spawn |

玩家预制体登记在 `Assets/DefaultNetworkPrefabs.asset`。登记的必要性在于：服务器只广播"生成索引 + `clientId`"，客户端必须能在本地按同一索引找到同一个预制体，双方才认为生成的是同一个对象。

【作图说明】图 4-x 网络对象注册关系图：`NetworkManager → DefaultNetworkPrefabs → Player.prefab(NetworkObject) → 组件列表`。

### 1.2 连接建立

```csharp
// Host：绑定本机全部网卡的 7777 端口，同时启动服务器与本地客户端
_selfTransport.SetConnectionData("0.0.0.0", 7777, "0.0.0.0");
NetworkManager.Singleton.StartHost();

// Client：填写房主 IP
_selfTransport.SetConnectionData(ip.Trim(), 7777);
NetworkManager.Singleton.StartClient();
_connectTimeout = StartCoroutine(ConnectTimeout());   // 15 秒连接超时
```

`StartHost()` 使房主同时具备两种身份：UDP 监听端（服务器）与 `clientId = 0` 的本地客户端。`StartClient()` 触发 NGO 握手，成功后分配 `clientId`（房主 0、加入者 1）并回调 `OnClientConnectedCallback`。

连接超时的实现：协程等待 15 秒，若仍未 `IsConnectedClient`，则调用 `Shutdown()` 并主动返回大厅。之所以要"主动返回"，是因为**客户端从未真正建立连接时，`Shutdown` 不保证触发断线回调**，不能依赖回调兜底。

### 1.3 玩家对象的生成与身份确定

连接成功后不写任何 `Instantiate` 代码：NGO 依据 `NetworkManager` 上配置的 Player Prefab **自动生成玩家对象**，并回调：

```csharp
public override void OnNetworkSpawn()
{
    int pNum = (int)OwnerClientId;      // 0 → P1（房主），1 → P2（加入者）
    if (IsServer) { PlayerNumber.Value = pNum; SyncPos.Value = spawnPos; }
    ...
}
```

全项目的玩家身份都来自 `OwnerClientId`，而非对象名或场景顺序。出口判定、任务确认、压力板归属、推箱校验均以此为唯一依据。

### 1.4 状态同步：`NetworkVariable`

声明时即固定读写权限：

```csharp
NetworkVariable<bool> _isPressed = new NetworkVariable<bool>(
    false,
    NetworkVariableReadPermission.Everyone,      // 所有端可读
    NetworkVariableWritePermission.Server);      // 仅服务器可写
```

运行机制分四步：

1. 服务器执行 `_isPressed.Value = true`；
2. NGO 将该变量标记为 **dirty**，在下一个网络 tick 只打包发生变化的变量（增量复制，而非全量快照）；
3. 客户端收到后写入本地副本；
4. 客户端触发 `OnValueChanged`，由表现层刷新颜色、动画、音效。

订阅与退订必须成对，否则重连后回调会叠加：

```csharp
public override void OnNetworkSpawn()   { _isPressed.OnValueChanged += OnPressedChanged; }
public override void OnNetworkDespawn() { _isPressed.OnValueChanged -= OnPressedChanged; }
```

项目中使用该机制同步的状态包括：门开关、压力板按压、出口占用、玩家朝向、任务选择与确认状态、箱子持有者。

### 1.5 客户端请求：`ServerRpc`

```csharp
[ServerRpc(RequireOwnership = false)]
void TryPickupServerRpc(ServerRpcParams rpcParams = default)
{
    ulong senderId = rpcParams.Receive.SenderClientId;          // 服务器侧认定的真实发送者
    var playerObj = NetworkManager.Singleton.SpawnManager.GetPlayerNetworkObject(senderId);
    if (playerObj == null) return;
    if (Vector3.Distance(transform.position, playerObj.transform.position) > pickupRange) return;   // 距离校验
    _isHeld.Value = true;
    _holderId.Value = senderId;
}
```

实现要点：

- **方法名必须以 `ServerRpc` 结尾**，NGO 在编译期通过代码生成自动产生发送桩与接收桩，方法参数自动序列化；
- `RequireOwnership = false` 用于调用者并非对象拥有者的情况（如场景中的箱子归服务器所有）；
- 发送者身份必须从 `rpcParams.Receive.SenderClientId` 获取，不能使用 `NetworkManager.LocalClientId`（后者是"本机视角"，在服务器上无法得到真实来源）；
- 服务器在写状态前做**软校验**（存在性、距离、数值范围），这是抗作弊的实现落点。

交互类逻辑采用"**RPC 薄壳 + 业务方法**"的组织方式，便于单独测试服务器逻辑：

```csharp
[ServerRpc(RequireOwnership = false)]
void DoorInteractServerRpc(int doorId, ServerRpcParams rpcParams = default)
{
    ...校验...
    HandleDoorPress(rpcParams.Receive.SenderClientId);   // 业务逻辑在普通方法中
}
void HandleDoorPress(ulong sender) { ... }               // 无网络依赖，可直接调用验证
```

### 1.6 服务器通知：`ClientRpc`

```csharp
// 广播：所有客户端都收到
[ClientRpc]
void ReceiveChatClientRpc(ulong senderId, string sender, string message)
    => ChatSystem.Instance?.OnMessageReceived(senderId, sender, message);

// 定向：只发给指定客户端
var rpc = new ClientRpcParams
{
    Send = new ClientRpcSendParams { TargetClientIds = new[] { OwnerClientId } }
};
ApplyTeleportClientRpc(pos, rpc);
```

广播用于"所有人都要知道"的事件（聊天、谜底揭示、倒计时提示）；定向用于"只与该玩家有关"的事件（传送落地）。

### 1.7 位置同步

采用"拥有者本地驱动 + 定时/位移双条件节流 + 非拥有者覆盖"的方案：

```csharp
// 拥有者：本地移动后节流上报
_syncTimer += Time.deltaTime;
bool movedEnough = (transform.position - _lastSentPos).sqrMagnitude > 0.01f;   // 位移约 0.1m
if (_syncTimer < _syncInterval /*0.1s*/ && !movedEnough) return;
if (IsServer) { SyncPos.Value = pos; SyncRot.Value = rot; }
else          { UpdateTransformServerRpc(pos, rot); }

// 非拥有者：物理帧中按同步值覆盖
void FixedUpdate()
{
    if (IsOwner) return;
    transform.position = SyncPos.Value;
    transform.rotation = SyncRot.Value;
    _animator.SetInteger("facing", SyncFacing.Value);
}
```

带宽控制效果：静止时零发送，移动时上限 10 次/秒，较"每帧 60 次"下降约一个数量级。动画同步不传输动画时间轴，只同步一个 `int facing`（0 待机 / 1 下 / 2 上 / 3 左 / 4 右），由各端本地驱动同一个 Animator。

### 1.8 传送的实现：两路通知

```csharp
public void ServerTeleport(Vector3 pos)
{
    if (!IsServer) return;
    _cc.enabled = false;                 // CharacterController 需关闭后改坐标，再开启
    transform.position = pos;
    _cc.enabled = true;

    SyncPos.Value = pos;                 // 第 1 路：通知其他客户端
    ApplyTeleportClientRpc(pos, new ClientRpcParams {   // 第 2 路：定向通知拥有者本人
        Send = new ClientRpcSendParams { TargetClientIds = new[] { OwnerClientId } } });
}
```

必须发两路的原因由 1.7 的机制决定：拥有者的位置由本地驱动、**从不读取 `SyncPos`**，因此仅写 `NetworkVariable` 对本人无效，必须再定向发送一次 `ClientRpc`。任何"本地直接修改非拥有者坐标"的做法都会被下一个物理帧的 `SyncTransform` 覆盖。

### 1.9 场景同步

```csharp
// 仅服务器调用，客户端自动跟随
var status = NetworkManager.Singleton.SceneManager.LoadScene("Level1", LoadSceneMode.Single);

void OnSceneLoadComplete(ulong clientId, string sceneName, LoadSceneMode mode)
{
    if (clientId != NetworkManager.Singleton.LocalClientId) return;   // 只处理本机
    ...
}
```

关卡加载后还需要解决一个副作用：玩家的 `NetworkObject` **跨场景保留**，`OnNetworkSpawn` 一生只执行一次，因此换场景后不会自动回到出生点。实现上由服务器显式补传：

| 场景 | 补传位置 | 代码位置 |
|---|---|---|
| 大厅 | 殿内固定出生点 | `GameManager.OnSceneLoadComplete` |
| 各关卡 | 本关配置的 `_p1Spawn / _p2Spawn` | `LevelManager.OnNetworkSpawn` |

### 1.10 聊天中继

```csharp
[ServerRpc(RequireOwnership = false)]
public void SendChatServerRpc(string sender, string message, ServerRpcParams rpcParams = default)
    => ReceiveChatClientRpc(rpcParams.Receive.SenderClientId, sender, message);

[ClientRpc]
void ReceiveChatClientRpc(ulong senderId, string sender, string message)
    => ChatSystem.Instance?.OnMessageReceived(senderId, sender, message);
```

服务器转发时会**附带可信的 `SenderClientId`**：消息内容由客户端提供，但"是谁发的"由服务器认定，接收端据此着色（P1 与 P2 不同颜色），客户端无法冒充他人。

### 1.11 断线处理：状态对账

```csharp
void OnClientDisconnected(ulong clientId)
{
    if (!NetworkManager.Singleton.IsServer) { ReturnToLobbyAfterDisconnect(); return; }   // 客户端：回大厅

    GameHUD.Instance?.ShowToast($"P{clientId + 1} 已断开连接", 3f);
    LevelManager.Instance.OnPlayerDisconnected((int)clientId);            // 清出口占用
    foreach (var npc in FindObjectsOfType<NpcDialogue>())
        npc.OnPlayerDisconnected(clientId);                               // 取消待确认任务
}
```

对账的必要性：玩家对象销毁**不会触发 `OnTriggerExit`**，基于触发器的状态（出口占用、任务等待）可能永久保持，导致谜题锁死。因此所有由"玩家存在"推导出的状态，都在断线回调中显式清除。

压力板进一步从设计上规避该问题：不使用 `OnTriggerEnter/Exit` 计数，而是由服务器每 0.2 秒执行一次 `Physics.OverlapBoxNonAlloc`，重建占位者集合（`HashSet<NetworkObjectId>`）。玩家掉线后自然不在重叠结果中，状态自动释放。

### 1.12 联机实现小结

| 环节 | 实现手段 |
|---|---|
| 连接 | `UnityTransport.SetConnectionData` + `StartHost/StartClient` + 15s 超时 |
| 身份 | `OwnerClientId`（0=P1，1=P2） |
| 状态 | `NetworkVariable<T>`（Server 写、增量复制、`OnValueChanged`） |
| 请求 | `[ServerRpc(RequireOwnership=false)]` + `SenderClientId` + 服务器校验 |
| 通知 | `[ClientRpc]`；点对点用 `TargetClientIds` |
| 位置 | 0.1s / 0.1m 双条件节流 + 非拥有者 `FixedUpdate` 覆盖 |
| 传送 | `SyncPos`（广播）+ 定向 `ClientRpc`（本人） |
| 场景 | `SceneManager.LoadScene` 服务器发起 + `OnLoadComplete` 本机处理 + 出生点补传 |
| 聊天 | `ServerRpc → ClientRpc` 中继，附可信发送者 ID |
| 断线 | `OnClientDisconnectCallback` 对账清除状态 |

## 2 数据库实现

### 2.1 选型与初始化

后端采用 **SQLite 单文件数据库**（`server/data/game.db`），通过 `better-sqlite3` 访问。选型依据：零安装、单文件可随项目部署、满足两人房间的并发量级、同步 API 使业务代码顺序可读。

```js
const db = new Database(path.join(__dirname, 'data', 'game.db'));   // 文件不存在则自动创建
db.pragma('journal_mode = WAL');        // 写前日志：读写并行，降低锁表概率
db.pragma('foreign_keys = ON');         // SQLite 默认关闭外键，必须显式开启才能级联删除
db.exec(`CREATE TABLE IF NOT EXISTS ...`);   // 幂等建表，可重复启动
```

初始化阶段同时完成三件事：

1. **目录自建**：`fs.mkdirSync(dataDir, { recursive: true })`，避免全新部署时因目录不存在而崩溃；
2. **结构迁移**：用 `PRAGMA table_info(rooms)` 检查列，缺失则 `ALTER TABLE ... ADD COLUMN last_activity`；
3. **种子数据**：关卡配置用 `INSERT OR IGNORE` 幂等写入，重复启动不会产生重复记录。

### 2.2 表结构

| 表 | 关键字段 | 说明 |
|---|---|---|
| `users` | `username UNIQUE`、`password_hash`、`created_at` | 账号表，仅存 bcrypt 哈希 |
| `rooms` | `host_user_id`、`host_ip`、`host_username`、`max_players=2`、`current_players`、`status`、`last_activity` | 房间簿记，`host_ip` 是联机交接点 |
| `room_members` | 复合主键 `(room_id, user_id)` | 成员表，复合主键天然防重复入房 |
| `players` | `room_id`、`user_id`、`position`、`rotation`、`is_moving`、`move_x`、`move_y` | 对局留痕（建房/加房时各写一条，不做实时更新） |
| `missions` | `mission_name`、`objective`、`spawn_p1`、`spawn_p2` | 关卡配置 |
| `mechanisms` | `mission_id`、`mech_type`、`mech_state`、`linked_doors` | 机关配置与接线 |
| `items` | `mission_id`、`item_type`、`position`、`holder_id` | 道具配置 |
| `chat_messages` | `sender_id`、`sender`、`content`、`send_time` | 聊天留痕表（运行期聊天走 Netcode，本表当前不作实时写入） |

实体关系：`users 1—N rooms`（房主）、`users N—N rooms`（经 `room_members`）、`rooms 1—N players`、`missions 1—N mechanisms / items`。所有以 `room_id` 为外键的表均声明 `ON DELETE CASCADE`，删除房间时成员与对局记录自动清除。

【作图说明】图 4-y 数据库 E-R 图：以 `users`、`rooms`、`room_members` 为核心三角，右侧并列 `missions → mechanisms / items`，下方挂 `players` 与 `chat_messages`；`rooms.host_ip` 用高亮标注为"联机交接字段"。

### 2.3 数据访问方式

统一使用**预处理语句 + 参数绑定**，值不拼接进 SQL 字符串：

```js
db.prepare('SELECT id, username, password_hash FROM users WHERE username = ?').get(username);
db.prepare('INSERT INTO users (username, password_hash) VALUES (?, ?)').run(username, hash);
db.prepare('SELECT ... FROM rooms WHERE status != ?').all('closed');
```

| 方法 | 返回 | 项目中的用途 |
|---|---|---|
| `.run(...)` | `{ changes, lastInsertRowid }` | 插入/更新；建房后用 `lastInsertRowid` 作为 `roomId` 返回 |
| `.get(...)` | 单行对象或 `undefined` | 按用户名查账号、按 ID 查房间 |
| `.all(...)` | 数组 | 房间列表、种子校验、表结构检查 |

### 2.4 认证与鉴权

**注册与登录（`routes/auth.js`）**

```js
const hash  = bcrypt.hashSync(password, 10);                          // 加盐慢哈希
const ok    = bcrypt.compareSync(password, user.password_hash);
const token = jwt.sign({ userId, username }, process.env.JWT_SECRET, { expiresIn: '24h' });
res.json({ success: true, token, username });
```

**请求鉴权（`middleware/auth.js`）**

```js
function authMiddleware(req, res, next) {
  const header = req.headers['authorization'];
  if (!header || !header.startsWith('Bearer ')) return res.status(401).json({ ... });
  const token = header.slice(7);
  try { req.user = jwt.verify(token, process.env.JWT_SECRET); next(); }
  catch { return res.status(401).json({ success: false, error: '认证令牌无效或已过期' }); }
}
router.use(authMiddleware);        // 房间路由整体挂载，后续 SQL 中的 req.user.userId 可信
```

### 2.5 房间生命周期

**建房**（`POST /api/rooms`）

```js
// ① 清理该用户此前处于等待状态的房间（不删除进行中的房间）
DELETE FROM rooms WHERE host_user_id = ? AND status = 'waiting';
// ② 创建房间
INSERT INTO rooms (name, host_user_id, host_ip, host_username, max_players, current_players, status)
VALUES (?, ?, ?, ?, 2, 1, 'waiting');
// ③ 房主计入成员
INSERT INTO room_members (room_id, user_id) VALUES (?, ?);
// ④ 写入对局留痕（失败静默，不影响建房）
INSERT INTO players (room_id, user_id, position, rotation, is_moving, move_x, move_y) VALUES (?, ?, '', 0, 0, 0, 0);
```

**加房**（`POST /api/rooms/:id/join`）

```js
// ① 房间存在且未关闭  ② 未满员
if (room.current_players >= room.max_players) return res.status(403).json({ error: '房间已满' });
// ③ 写入成员（复合主键 + OR IGNORE 保证幂等）
INSERT OR IGNORE INTO room_members (room_id, user_id) VALUES (?, ?);
// ④ 人数 +1、状态改为 playing、刷新活动时间
UPDATE rooms SET current_players = current_players + 1, status = 'playing' WHERE id = ?;
UPDATE rooms SET last_activity = CURRENT_TIMESTAMP WHERE id = ?;
// ⑤ 返回房主 IP —— 客户端据此启动 Netcode 直连
res.json({ success: true, hostIp: room.host_ip, host_username: room.host_username });
```

**离房**（`POST /api/rooms/:id/leave`）

```js
// ① 校验调用者确实是该房间成员（防越权修改他人房间）
const membership = db.prepare('SELECT * FROM room_members WHERE room_id = ? AND user_id = ?').get(...);
if (!membership) return res.status(404).json({ error: '你不在该房间中' });

// ② 房主离开 → 删除房间（成员/对局记录级联删除）
if (room.host_user_id === req.user.userId) db.prepare('DELETE FROM rooms WHERE id = ?').run(roomId);
// ③ 成员离开 → 删成员、人数 -1、状态回 waiting；人数归零则删除房间
else { ... UPDATE rooms SET current_players = MAX(current_players - 1, 0), status = 'waiting' ... }
```

**关房**（`DELETE /api/rooms/:id`）：仅房主可调用，否则返回 403。

### 2.6 定时清理

```js
const ROOM_IDLE_TIMEOUT_MS = 10 * 60 * 1000;   // 10 分钟无活动视为过期
const SWEEP_INTERVAL_MS    = 5  * 60 * 1000;   // 每 5 分钟扫描一次

function sweepStaleRooms() {
  const cutoff = new Date(Date.now() - ROOM_IDLE_TIMEOUT_MS).toISOString();
  db.prepare(`DELETE FROM rooms WHERE status != 'closed' AND last_activity < ?`).run(cutoff);
}
setInterval(sweepStaleRooms, SWEEP_INTERVAL_MS);
```

`last_activity` 在加房/离房时由 `touchRoom()` 刷新，因此"仍有人使用"的房间不会被误删。

### 2.7 限流与启动自检

```js
// 启动自检：密钥缺失或过弱直接拒绝启动，避免令牌可被伪造
if (!process.env.JWT_SECRET || process.env.JWT_SECRET.startsWith('change_this')
    || process.env.JWT_SECRET.length < 32) { console.error('[FATAL] ...'); process.exit(1); }

// 限流：登录/注册 10 次/分钟/IP；房间接口 60 次/分钟/IP
app.use('/api/auth',  authLimiter,  authRoutes);
app.use('/api/rooms', roomsLimiter, roomRoutes);
```

### 2.8 数据库实现小结

| 环节 | 实现手段 |
|---|---|
| 建库 | SQLite 单文件 + WAL + 外键开启 + `CREATE TABLE IF NOT EXISTS` |
| 升级 | `PRAGMA table_info` + `ALTER TABLE` 补列；种子用 `INSERT OR IGNORE` |
| 查询 | `db.prepare().run/get/all` + 参数绑定 |
| 认证 | bcrypt(cost 10) 存哈希；`jwt.sign` 签发 24h 令牌 |
| 鉴权 | `Bearer` 头 + `jwt.verify` 中间件 → `req.user` |
| 建房 | 清旧等待房 → `INSERT rooms` → `INSERT room_members` → `INSERT players` |
| 加房 | 满员校验 → `INSERT OR IGNORE` → 人数 +1 / 状态 playing → 返回 `host_ip` |
| 离房 | 成员校验 → 房主删房（级联）或成员减员 → 归零删房 |
| 清理 | `setInterval` 5 分钟扫描，删除 10 分钟无活动房间 |
| 防护 | 启动自检 JWT 密钥强度 + 双档限流 + 越权校验 |

## 3 客户端 HTTP 调用实现

`ApiClient` 是静态工具类，统一封装请求构造、鉴权头、超时与错误处理。

```csharp
var req = new UnityWebRequest(ApiBase + path, "POST");
req.uploadHandler   = new UploadHandlerRaw(Encoding.UTF8.GetBytes(jsonBody));
req.downloadHandler = new DownloadHandlerBuffer();
req.SetRequestHeader("Content-Type", "application/json");
if (!string.IsNullOrEmpty(Token)) req.SetRequestHeader("Authorization", "Bearer " + Token);

req.timeout = 10;                       // 统一超时
yield return req.SendWebRequest();
bool success = req.result == UnityWebRequest.Result.Success;

if (!success && req.responseCode == 401) {   // 令牌失效：清除本地认证并回到登录界面
    ClearAuth();
    UIManager.Instance?.ShowLogin();
}
req.Dispose();
callback?.Invoke(success, body);
```

配套实现：

- **令牌持久化**：`PlayerPrefs.SetString("jwt_token", token)` + `Save()`，下次启动由 `ApiClient.IsLoggedIn` 直接进入大厅（自动登录）；
- **协程宿主**：静态类无法 `StartCoroutine`，`StaticCoroutine.Start()` 懒创建一个隐藏的 `DontDestroyOnLoad` GameObject 作为协程载体；
- **错误抽取**：请求失败时优先读取响应体中的 JSON `error` 字段，取不到才回退到 `req.error`。

## 4 两条通道的衔接

两条通道通过两个值完成交接：

```csharp
// 建房成功：roomId 用于云端销账，随后启动 UDP 服务端
GameManager.Instance.CurrentRoomId = roomId;
GameManager.Instance.StartHost();

// 加房成功：从云端取得门牌号，随后启动 UDP 客户端
RoomApi.JoinRoom(roomId, (success, hostIp, hostName, error) => {
    if (success) { GameManager.Instance.CurrentRoomId = roomId; GameManager.Instance.Connect(hostIp); }
});
```

| 值 | 来源 | 去向 | 作用 |
|---|---|---|---|
| `roomId` | `POST /rooms` 返回 | `GameManager.CurrentRoomId` | 离房/关房时向云端销账 |
| `hostIp` | `POST /rooms/:id/join` 返回 | `UnityTransport.SetConnectionData` | 启动 Netcode 直连 |

【作图说明】图 4-z 联机时序图：`P1(Host) / 云服务器+SQLite / P2(Client)` 三条泳道，自上而下依次为：登录 → 建房 → `StartHost` → 加载大厅 → P2 登录 → 拉房间列表 → 加房（返回 `hostIp`）→ `StartClient` → UDP 握手 → 场景同步 → 游戏期通信 → 断线对账 → 离房。

## 5 一致性与安全的实现要点

| 目标 | 具体手段 |
|---|---|
| 状态一致 | 关键状态只由服务器写 `NetworkVariable`；客户端只发 `ServerRpc` |
| 防作弊 | 服务器在写状态前校验发送者存在性、距离、数值范围；谜题进度只存服务器 |
| 防重复入房 | `room_members` 复合主键 `(room_id, user_id)` + `INSERT OR IGNORE` |
| 防越权 | 离房/关房先校验成员身份或房主身份 |
| 防注入 | 预处理语句 + 参数绑定 |
| 防暴力破解 | bcrypt 慢哈希 + 10 次/分钟/IP 限流 |
| 防伪造令牌 | 启动时校验 `JWT_SECRET` 长度，过弱拒绝启动 |
| 防账号枚举（登录侧） | 用户不存在与密码错误返回同一文案 |
| 防数据残留 | 外键 `ON DELETE CASCADE` + 定时清扫过期房间 |
| 防状态卡死 | 断线回调对账；压力板改用重叠查询而非触发器计数 |

## 6 已知局限与改进方向

| # | 局限 | 改进方案 |
|---|---|---|
| 1 | 业务通道为 HTTP 明文，JWT 明文存 `PlayerPrefs` | 部署 HTTPS 反向代理；令牌改为加密存储 |
| 2 | 注册重名返回 409 与"用户名已存在"文案，存在账号枚举风险 | 统一模糊文案或改为邮箱验证 |
| 3 | `bcrypt.hashSync / compareSync` 同步执行，阻塞事件循环 | 改用异步版本或 `worker_threads` |
| 4 | 建房涉及多条写入，未显式包裹事务 | 使用 `db.transaction(fn)` 包裹，保证原子性 |
| 5 | 玩家位置由客户端上报，服务器未做位移校验 | 增加单帧位移上限校验，超限回滚；`ServerTeleport` 走白名单 |
| 6 | 无心跳与重连机制 | 依赖 NGO 内建超时；可在应用层增加心跳与断线重连提示 |
| 7 | `chat_messages` 表建而未用 | 若需聊天审计，可在 `ReceiveChatClientRpc` 前由服务器落库 |

## 2. 高频追问 Q&A

**Q1：为什么用"服务器权威"？客户端直接改不行吗？**
A：解谜游戏的核心是"改状态能不能过关"，一旦客户端能自己开门/改谜题进度，作弊就是零成本。所以约定：**状态只由服务器写（NetworkVariable）、客户端只发请求（ServerRpc）**。同时把"进度"（台词下标、已搜索集合、门开关）全部放在服务器，客户端只是显示器。

**Q2：位置同步为什么要节流？怎么节流？**
A：`PlayerMove.UpdateTransform` 用**双条件**——距上次发送 ≥0.1s **或**位移平方 >0.01（≈0.1m）才发。静止、微动都不发，走动时 ≤10 次/秒。相比每帧 60 次 RPC，带宽降一个数量级；`SyncPos/SyncRot` 是 NetworkVariable（服务器只转发最新值，天然合并），客户端位置走 `UpdateTransformServerRpc`。

**Q3：为什么传送一定要走 `PlayerMove.ServerTeleport`？**
A：因为 owner 的位置**由自己本地驱动、从不读 `SyncPos`**，而非 owner 每物理帧被 `SyncPos` 硬覆盖。所以：直接改 transform → 被同步拉回；只写 NetworkVariable → 对 owner 无效。因此 `ServerTeleport` 做两件事：写 `SyncPos`（通知别人）+ 发 **定向 ClientRpc** 给 `OwnerClientId`（通知本人）。这是"NetworkVariable 对 owner 无效"的补位写法。

**Q4：压力板为什么不用 `OnTriggerEnter` 计数？**
A：三个原因：① 被服务器传送/瞬移的 CharacterController 触发不可靠、会漏；② 计数器会被重复事件破坏；③ **玩家对象销毁不会触发 `OnTriggerExit`**，计数会永久卡死把谜题锁死。改用**服务器每 0.2s 的 `OverlapBoxNonAlloc` 重建 `HashSet<NetworkObjectId>`**：幂等、无重复计数、掉线即自然消失；且用 `SetEquals` 判断"无变化就不写 NetworkVariable"省带宽。

**Q5：门的 AND / OR 是怎么实现的？**
A：`LockedDoor._requireAllPlates`：`false` = 任一关联板按下即开（OR，实现"一人踩板、对面开门"的看门人机制）；`true` = 全部关联板同时按下才开（AND，实现"两人/双权重同时"的收尾）。而且 `_plates[]` **允许指向对面走廊的板** —— 你需要的门只能由同伴打开，这是第三关的设计核心。

**Q6：为什么箱子位置用 `NetworkTransform` 而不用 NetworkVariable？**
A：按**数据特征**选同步方式：位置是高频连续量，`NetworkTransform` 内置插值/压缩/dirty 判断，不要自己造；"是否被持有/被谁持有"是低频离散量，用 `bool` + `ulong` 两个 NetworkVariable 最省。搬运时服务器把箱子 Lerp 到持有者前方，位置由 NetworkTransform 自动复制，**不需要每帧 RPC**。

**Q7：客户端玩家也能推箱子？**
A：能。CharacterController 本身不推动刚体，所以 `PlayerMove.OnControllerColliderHit` 显式施加：**主机直接 `cube.ApplyPush(v)`；客户端玩家 0.08s 节流后 `PushCubeServerRpc` 中继给服务器**，服务器校验"发送者真实存在 / 距箱子 ≤1.6m / 速度在 0.01~100"后才施加。曾经的坑：写成 `if (!IsServer) return;` 就只有主机玩家推得动。

**Q8：为什么进关卡后要服务器显式传送玩家？**
A：玩家的 NetworkObject **跨场景保留**（不随 Single 模式场景卸载而销毁），`OnNetworkSpawn` 一生只跑一次 → 换场景不会自动落在出生点。所以每进场景由服务器调用 `ServerTeleport`：大厅在 `GameManager.OnSceneLoadComplete`，各关卡在 `LevelManager.OnNetworkSpawn`（用各关自己的 `_p1Spawn/_p2Spawn`）。

**Q9：NPC 任务确认的双人协议怎么保证不错乱？**
A：只用一个管理器内的两个 NetworkVariable 当状态机：`_selectedMission`（-1 未选 / 任务号）+ `_confirmState`（0 无 / 1 待确认 / 2 已确认 / 3 已拒绝）。服务器负责：收到选择后置 1 并起 **30s 超时协程**；P2 回复后置 2（→ `LoadLevel`）或 3（→ 复位让 P1 重选）；玩家掉线由 `GameManager` 调 `OnPlayerDisconnected` 置 0。UI 只是 `OnValueChanged` 的投影。

**Q10：第一关"钥匙不在房间里"这个谜题是怎么实现的？**
A：`IRoomInteractable` 接口 + 静态 `Registry`/`ById` 注册表：每个调查物自注册，管理器统一做"最近目标 E 键交互"。服务器处理 `InvestigateServerRpc`，推进台词下标、把 `SearchKey` 加入 `HashSet`；当已搜索数 ≥ `RequiredTargetCount()`（= 场景里 `IsRequiredForHint` 的调查物数量）时置 `_hintRevealed = true` → 全员同步，墙上金字出现 + 台词框播报。此时再交互大门，服务器发现"已揭示"，就把 `_doorOpened` 置真并播放"锁只是画上去的"揭示台词，门绕铰链摆开。

**Q11：相机为什么会"掉头/操作反转"？怎么修的？**
A：早期镜头被物理挤过北墙后会跑到玩家南侧，相机 yaw 翻 180° → W/S 反向。修法不是调参而是**钳制视线方向**：`desired.z ≤ player.z - 0.45`（镜头永在玩家北侧）、`lookDir.z ≥ 0.35`（视线永不掉头）、`desired.y ≥ player.y + 2.8`（最低高度），再加"距离 >6m 直接就位（出生/传送不甩尾）+ 指数阻尼 `1-exp(-k·dt)`（帧率无关）"。

**Q12：加载进度条是真的吗？**
A：**不是真进度**。Netcode 不暴露场景加载百分比，所以进度条是化妆动画：爬向 90%（越接近越慢），收到本机 `OnLoadComplete` 立刻置 100% 再淡出。这一点我会主动说明——它的作用是消除"卡住/没反应"的焦虑，而不是测量。

**Q13：聊天为什么是服务器中继而不是直接 P2P 发送？**
A：因为本项目是"Host 即是服务器"的星型拓扑（NGO 的 Host 同时是 Server），所有 RPC 本来就必须经过服务器；中继的额外价值是**服务器能把可信的 `SenderClientId` 一起广播**，接收端据此给消息着色（P1 琥珀 / P2 灰蓝），而客户端无法伪造别人的 ID。

**Q14：后端为什么不存游戏数据？**
A：定位是"**房间介绍所**"：解决"两个玩家怎么找到对方"，返回 `host_ip` 后就走 Netcode UDP 直连，游戏帧数据完全不过云。好处是服务器零游戏负载、延迟最低、成本最低；代价是要求 Host 可被直连，所以保留了"手输 IP 直连"入口和 TCP 3001 的 `EchoTester` 自检工具。

**Q15：后端安全做了哪些？还差哪些？**
A：已做：JWT（24h 过期）鉴权所有房间接口、`JWT_SECRET` 弱/缺省时**拒绝启动**、bcrypt(cost 10) 存哈希、`express-rate-limit`（登录注册 10 次/分/IP、房间 60 次/分/IP）、登录失败统一文案不泄露账号存在性、离开房间校验成员身份防越权、`net.isIP` 校验 hostIp 格式。仍缺（如实说）：HTTP 明文 + JWT 明文存 `PlayerPrefs`（应上 HTTPS）、注册 409 会暴露用户名存在性、`bcrypt.hashSync/compareSync` 同步阻塞事件循环（应改异步）。

**Q16：HD2D 像素化实现了吗？**
A：骨架实现了（3D 场景 + 2D 像素精灵 + 固定俯角相机 + 三档 URP 质量 + 像素化后处理脚本 `PixelationFeature`），但**后处理当前未生效**，已定位到四个具体原因：① Feature 未挂到任何 URP Renderer；② 配套 `Pixelation.shader` 还是旧式顶点输入，不匹配 URP 14 `Blitter` 的 `DrawProcedural`（应改 `GetFullScreenTriangleVertexPosition(input.vertexID)`）；③ 片元采样 `_MainTex` 而 Blitter 绑的是 `_BlitTexture`（TexelSize 恒 0 → 除零）；④ `Shader.Find("Hidden/Pixelation")` 构建时可能被剔除（应改序列化引用或加 Always Included）。

**Q17：为什么第三关要做成两条一模一样的走廊？**
A：因为第三关的设计目标是"把协作做成**必须**而不是可选"：两条完全对称、互不可见的走廊（只能靠 T 聊天沟通），每道闸门都由**对面走廊或两厅共同**的机关控制 —— 一个人物理上无法单独推进。三条协作点分别是"看门人"（一人踩板开对面门）、"传递搬运"（唯一的箱子要经中墙传递窗递给对面）、"同时操作"（出口门是 AND 双板）。

**Q18：项目里已有哪些设计模式？**
A：单例（常驻服务，`OnDestroy` 清 Instance）、服务器权威、观察者（`OnValueChanged` 订阅/退订成对 + C# `event` 解耦 UI）、接口+注册表（`IRoomInteractable`）、推 vs 拉两种机关接线范式、节流/阈值同步、定向 RPC、横切关注点集中（`ApiClient`）、优雅降级（Toast 兜底/空列表占位/手输 IP）、幂等初始化（`CREATE TABLE IF NOT EXISTS` + `INSERT OR IGNORE`）。

## 4. 术语中英对照（评委可能用英文问）

| 中文 | 英文 / 代码名 | 说明 |
|---|---|---|
| 服务器权威 | Server-Authoritative | 状态只由服务器写 |
| 网络变量 | `NetworkVariable<T>` | 服务器写 → 全员读的状态同步 |
| 服务器远程调用 | `ServerRpc` | 客户端 → 服务器请求 |
| 客户端远程调用 | `ClientRpc` | 服务器 → 客户端通知（可定向 `TargetClientIds`） |
| 拥有者 | `OwnerClientId` / `IsOwner` | 一个网络对象在某客户端上的"本人副本" |
| 生成 / 销毁 | `OnNetworkSpawn` / `OnNetworkDespawn` | 订阅与退订必须成对 |
| 场景加载事件 | `OnLoadComplete` | 本机加载完成回调（只处理本机 clientId） |
| 中继 | Relay | 聊天由服务器整体广播，不做 P2P 直发 |
| 介绍所 | Matchmaking Lobby | 后端只做账号与房间匹配 |
| 令牌 | JWT (JSON Web Token) | 客户端登录凭证，24h 过期 |
| 密码哈希 | bcrypt | 加盐慢哈希，cost = 10 |
| 节流 | Throttling | 限制同步频率（0.1s / 0.08s） |
| 幂等 | Idempotent | 重复执行结果一致（`HashSet`、`INSERT OR IGNORE`） |
| 回差 | Hysteresis | 显隐切换留 0.5 缓冲，防闪烁 |

## 5. 答辩前 5 分钟自检

1. 后端可达：浏览器开 `http://8.130.65.176:3000/api/health` → `{"success":true,"message":"Server is running"}`。
2. 防火墙放行 **UDP 7777**；不确定就走"手输 IP 直连"。
